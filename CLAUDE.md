# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

DoodleSharp is a WPF 2D geometry visualization application that allows users to write C# code to create and visualize shapes on an interactive canvas. Users write code in `.cs` files, which are compiled at runtime using Roslyn and executed to render shapes.

## Tech Stack
- **Framework**: WPF on .NET 9.0
- **Code Editor**: AvalonEdit (6.3.0.90)
- **Code Compilation**: Roslyn CSharpCompilation (Microsoft.CodeAnalysis.CSharp 4.8.0)
- **Boolean Operations**: Clipper2
- **PDF Export**: PDFsharp
- **Coordinate System**: Mathematical (Y-up, origin at center)

### Module System
- **Entry Point**: `StartViz.Viz.Main()` in `StartViz.cs`
- All `.cs` files in the same directory are compiled together
- Available imports: `C2VGeometry`, `DoodleSharp.Animation`, `DoodleSharp.Console`

### Geometry namespace (`C2VGeometry`)
- **Single geometry namespace** for the whole solution. The old WPF-coupled `DoodleSharp.Geometry` was deleted; everything now uses `C2VGeometry`.
- **`VXYZ` is the coordinate value-type** (immutable-ish, not a `Shape`). **`VPoint` is only a drawable point marker.** Shape coordinates (`Center`, `Start`/`End`, polygon `Points`) are `VXYZ`; methods that take a position take `VXYZ`.
- **`CanvasRenderer` implements `C2VGeometry.IShapeRegistry`** and is set as `C2VGeometry.Shape.DefaultRegistry`, so `new VCircle(...)` auto-registers onto the canvas. There is no longer any `C2VGeometryAdapter`/conversion layer.
- **Charts (`C2VGeometry/Charts/`)** — `Chart` is a static helper that builds Chart.js-style charts (`Bar`/`Line`/`Scatter`/`Pie`/`Area`) by composing existing primitives (VLine, VRectangle, VPolyline, VPolygon, VText) into a single `VGroup`. To prevent the dozens of child shapes from auto-registering individually onto the canvas, the helper flips `Shape.AutoRegister = false` during construction and registers only the outer `VGroup`; the flag is restored in a `finally` block. This is the only sanctioned `Shape.AutoRegister` flip in user-construction code — never reintroduce it in `RayCaster` or other hot paths (see note 9). Pie sectors are polygon-approximated (no `VSector` shape).

### Shape System
- All shapes extend `Shape` abstract class which implements `IDrawable`
- Curve shapes (VLine, VCircle, VArc, etc.) also implement `ICurve` interface
- **Shapes auto-register on construction** - no need to call `Draw()`
- `Draw()` is kept for backwards compatibility but is a no-op
- Each shape overrides `GetControlPoints()` and `MoveControlPoint()` for interactive editing

### Code Execution (ModuleCompiler)
- Compiles all `.cs` files using Roslyn CSharpCompilation
- Creates in-memory assembly with unique name
- Invokes `StartViz.Viz.Main()` via reflection
- Uses collectible AssemblyLoadContext for proper unloading
- Shape ID counter resets on each code execution (IDs start from 1)

### Coordinate System
- Origin (0,0) at canvas center
- Y-axis points UP (mathematical, not screen coordinates)
- WorldToScreen/ScreenToWorld methods handle conversion
- Animation loop uses `CompositionTarget.Rendering` for vsync-aligned frame updates

### IntelliSense Engine (Editor/)
The IntelliSense system uses incremental Roslyn compilation for responsive completions:
- **CachedCompilationWorkspace** - Maintains a cached `CSharpCompilation` with incremental file updates (`UpdateFile`/`RemoveFile`). Avoids rebuilding the full compilation on every keystroke by using `ReplaceSyntaxTree`. Thread-safe.
- **RoslynCompletionService** - Provides context-aware completions via Roslyn's `Recommender` API. Detects context (generic type arguments, object initializers, attributes) and classifies symbol scope (Local/ClassMember/Imported/Global) for priority sorting.
- **FuzzyMatcher** - Subsequence fuzzy matching with scoring. Rewards prefix matches, word-boundary hits, camelCase alignment, and consecutive runs. Used to filter and rank completions as the user types.
- **DocumentationSidecar** - WPF `Popup` that displays XML documentation (signature, summary, parameters, returns) beside the completion window. Tracks the completion window position and updates on selection change.
- **CompletionData** - Extended with `SymbolScope`, `MatchScore`/`MatchPositions`, and `Symbol` properties. Renders match-highlight characters in bold within the completion list.

### WPF type aliases (in RenderCanvas.cs)
`RenderCanvas.cs` uses `C2VGeometry` types **directly** — there are no `*2D` geometry aliases anymore (no name clash). It only aliases the **WPF** types it also needs, to avoid clashing with geometry: `Point` = `System.Windows.Point`, plus `Brush`/`Pen`/`Color`/`Size`/`Rect` etc. from `System.Windows[.Media]`. World coordinates are `C2VGeometry.VXYZ`; screen coordinates are `System.Windows.Point`.

## Key Implementation Notes

**Note numbers are stable IDs, not positions.** Notes cross-reference each other by number, so a
number is never reused or renumbered. The gaps are notes that were deleted when the Animator
sub-app, the `SketchHost` isolation child, the Blazor web port and the MCP server were removed
from this fork; a new note takes the next unused number.

1. **In RenderCanvas.cs, alias the WPF types** (Point, Brush, …) so they don't clash; geometry types (`VXYZ`, `VCircle`, …) are used directly
2. **Y-coordinate is inverted** in WorldToScreen (mathematical coords)
3. **Syntax highlighting files** are embedded resources (EmbeddedResource in csproj)
4. **Colors** parsed via WPF ColorConverter - any named color works
5. **Working directory** is set to project folder during execution - relative paths resolve from there
6. **Use `VXYZ` for intermediate coordinates** — it's a plain value type and never registers. **`VLine.Internal(start, end)`** creates a *non-registering* `VLine` for any code that needs a `VLine` purely as a data container — a polygon/region's internal edge segments, tessellation, self-intersection scans. A plain `new VLine(...)` auto-registers with `Shape.DefaultRegistry` (= the canvas) and pollutes the scene with phantom segments rendered in the default color (see note 10 — `VPolygon.BuildCurvesFromPoints` and `Region.FromPolygon` shipped this bug; the polygon's outline rendered as separate default-cyan edge lines until they were switched to `VLine.Internal`).
7. **Every Draw* method in RenderCanvas must handle DrawFactor** - check `DrawFactor <= 0` for early return, implement partial drawing logic, and apply OffsetX/OffsetY for MoveAnimation support. See DrawPolyline as the reference pattern for segment-based shapes.
8. **ConsolePanel must NOT span into Auto grid rows** - placing it at `Grid.Row="4"` only (no RowSpan into the Auto row 3). Spanning into Auto rows causes WPF to measure the ListBox with infinite height, making the console expand to fit all content instead of scrolling.
9. **RayCaster (`C2VGeometry/Operations/RayCaster.cs`)** is the spatial accelerator for ray queries — flat-array BVH with SAH binning, iterative traversal with `stackalloc` stack, inline ray-vs-shape math for VLine/VCircle/VArc/VEllipse/VPolygon/VPolyline. It takes an **explicit shape collection**: `new RayCaster(IEnumerable<Shape> shapes, int leafSize = 8)` — there is no canvas-snapshot constructor (the library has no canvas). App callers pass `CanvasRenderer.Instance.GetShapes()`. **`VPoint` is always excluded** from the index (zero-area visual markers, not useful ray targets); shapes with non-finite bounds (VRay, VXLine) are excluded too. Never reintroduce the `Shape.AutoRegister` flip; the hot path is intentionally allocation-free and reentrant. The slab test branches on `double.IsInfinity(invD)` so degenerate AABBs and axis-aligned rays do not produce NaN — keep this fix even though `VPoint` exclusion makes the most common trigger disappear. Use `Refit()` for small movements; rebuild for large scene changes. Tests that touch the canvas singleton or `Shape.DefaultRegistry` live in the `"CanvasState"` xUnit collection (defined with `DisableParallelization = true`, in `Tests/CanvasStateCollection.cs`) and reset state in setup/teardown — keep new such test classes in the same collection.
10. **CurveIntersection self-intersection scans must not allocate `VLine`** in their inner loops. `IsPolylineSelfIntersecting`, `IsPolygonSelfIntersecting`, and `GetSegments` all use raw-double math via the private `SegmentsIntersectRaw`/`AppendRawSegments` helpers, plus `VLine.Internal` for any real `VLine` data containers. Reason: `VLine` auto-registers on construction, so the original O(N²) inner loop was dumping ~N²/2 phantom shapes onto the canvas — a 360-vertex polygon leaked ~65k shapes and turned a sub-millisecond computation into a multi-second one. Never reintroduce `new VLine(...)` in these paths. `SharedEndpointTouchOnly` preserves the original knot-vertex exemption from `IsOnlyAtSharedEndpoints`. (Single `C2VGeometry` namespace now — geometry auto-registers via `Shape.DefaultRegistry`, which the app sets to `CanvasRenderer.Instance`; there is no second namespace to mirror.) **Same class of bug, also fixed:** `VPolygon.BuildCurvesFromPoints` and `Region.FromPolygon`/`FromPolygonWithHoles` build their internal edge representation — those now use `VLine.Internal`, not `new VLine`, so a polygon/rectangle/region doesn't dump its edges onto the canvas. Guarded by `Tests/GeometryRegistryPollutionTests.cs`.
11. **`ICurve.SetBounds(double startParameter, double endParameter)`** trims a curve in place so [s, e] becomes the new [0, 1]; inputs are clamped to [0, 1] and swapped if reversed. **Open curves** (VLine, VArc, VEllipse, VPolyline, VBezier, VSpline) trim in place; **closed/infinite curves** (VCircle, VPolygon, VRay, VXLine) throw `NotSupportedException` because their trimmed form changes shape type — the message points callers to `SplitAtPoint`. Per-shape contracts that must hold: **VLine** reassigns its `Start`/`End` (now `VXYZ` value coordinates — `VXYZ` is immutable, so trimming sets new endpoint values); **VBezier** uses De Casteljau twice (split at e, then at s/e on the left piece) for an exact trim and likewise mutates P0..P3 in place; **VSpline** resamples at `numSpans × SegmentsPerSpan × (e − s)` points — never just keep the inner control points because Catmull-Rom tangents depend on neighbors and the trimmed curve will visibly bend away from the original. `_selfIntersecting` is non-readonly on VPolyline/VBezier/VSpline so SetBounds can recompute it. (Single `C2VGeometry` namespace.)
14. **`SharedEditorController` is the editor host glue, and is currently unused by the main window.** All editor wiring (TextMarkerService, bracket/selection renderers, semantic highlighter, inlay hints, code lens, snippets, folding, **realtime syntax check timer + squiggle markers**, mouse hover tooltips, context menu, F12/Shift+F12/F2/Ctrl+. key bindings, multi-cursor) is set up in one call to `_editorController.Initialize()`. Hosts wire their environment through callbacks: `GetActiveFilePath`, `GetWorkspace`, `GetActiveProject`, `SetStatusMessage`, `NavigateToLocation`, `ShowReferences`, `ApplyRefactoring`, `AutoRunCodeAsync`, `IsAutoUpdateEnabled`, `GetAutoUpdateDelayMs`. It was written as the shared host for a second app that no longer exists; `MainWindow.xaml.cs` still has its own parallel implementation inlined (see note 43), so **a fix to editor behaviour has to be made in both places** until one is retired. **Squiggle rendering** lives in `Editor/TextMarkerService.cs:Draw` — amplitude is 2px sitting just under the text baseline (not 1px below the line bottom, which was nearly invisible).
19. **CodeLens row positions must anchor to the live document, not store frozen offsets (`Editor/CodeLensProvider.cs`).** `CodeLensGenerator` renders the reference-count label by making the declaration line **2× tall** (`CodeLensElement` → `InlineObjectElement`, `Height = lineHeight * 2`) — there is no real document line, just an inline element painted in the empty upper half. `UpdateCodeLens` recompute is debounced on the 500 ms `_semanticUpdateTimer` (`SharedEditorController`), but AvalonEdit redraws touched lines on **every keystroke**. If each `CodeLensItem` holds a frozen absolute `Offset`, typing *above* a code-lensed declaration shifts the real offsets while the cached ones stay stale, so the tall row gets constructed on the wrong line and snaps back at the next debounce — visible vertical jitter while typing. Fix: each item carries a live `TextAnchor` (created via `_document.CreateAnchor`, `MovementType = AfterInsertion` so Enter-at-line-start pushes the row down *with* the declaration, `SurviveDeletion = true` so reading `.Offset` never throws), and `GetFirstInterestedOffset`/`ConstructElement` read `CurrentOffset` (the anchor's live offset). Anchors preserve relative order under edits, so the sorted item list stays sorted. **Never go back to plain `int Offset` lookups in the generator.** Shared `Editor/` source. **A second flicker source is *existence* (not position) toggling:** a structural syntax error nearby — e.g. an unclosed generic `List<VLine` mid-type — makes Roslyn's error recovery intermittently fail to parse the *following* `Setup()` as a `MethodDeclarationSyntax`, so on alternating recomputes the item is present/absent, the 2×-tall row blinks in and out, and the code below bounces. Fix in `UpdateCodeLens`: check `syntaxTree.GetDiagnostics().Any(d => d.Severity == DiagnosticSeverity.Error)`; on a **clean** parse swap `_items` outright (authoritative — renames/removals reconcile, counts refresh), on a **broken** parse call `MergePreservingExisting` which keeps every prior item (anchors hold their position) and only *adds* declarations whose `(Kind, SymbolName)` is new — it never removes an item during an error state. A failed build (`buildSucceeded == false`) leaves `_items` untouched rather than blanking the gutter. **Don't reintroduce the unconditional `_items = newItems` swap.**
20. **`RenderCanvas.OnMouseDown` grabs keyboard focus on any click** (`if (!IsKeyboardFocusWithin) Focus();`). The canvas's keyboard shortcuts (P/L/C/R drawing tools, Delete, A=select-all, Esc) are gated on `!CodeEditor.IsKeyboardFocusWithin` in the window key handler — so if a canvas click didn't move focus off the editor, those keys would just type into the editor. The canvas is `Focusable = true`; without the explicit `Focus()` on click, focus only moved mid-draw (a chicken-and-egg). Don't remove it.
21. **The compiler hardens against runaway user recursion via `Execution/StackGuardRewriter.cs` (namespace `DoodleSharp.Execution`).** User code runs **in-process**, and the runtimes already wrap it in `catch (Exception)` (`SketchRuntime.Tick`/`Start`; Main() mode's `TargetInvocationException` catch in `ModuleCompiler`) — but a **`StackOverflowException` is uncatchable** in .NET Core (the CLR fails fast and kills the process; AppDomains are gone). The rewriter injects `global::System.Runtime.CompilerServices.RuntimeHelpers.EnsureSufficientExecutionStack();` at the top of every method-like body (methods, local functions, constructors, operators, accessors, expression-bodied properties/indexers; lambdas/anonymous methods are intentionally left alone to avoid Func-vs-Expression overload shifts). That call throws a **catchable** `InsufficientExecutionStackException` *before* the stack overflows, so the existing `catch` stops execution and reports it. The injected statement carries **no trivia** so original statements keep their line numbers (runtime stack traces still map to the user's file); it does shift in-line **character offsets**, so it must only touch the **execute** path. **Wiring:** `ModuleCompiler.CreateCompilationAsync(project, injectStackGuards: true)` — the param defaults to `false` so the callers that map editor offsets onto the compilation (`CheckSyntaxAsync`, `RefactoringProvider` for F12/rename/find-refs, MainWindow) are unaffected (see note 41). The rewriter is reached by the Tests project through the main project reference (`Tests/StackGuardRewriterTests.cs`). This only covers the StackOverflow class — infinite loops, OOM, and native crashes would need process isolation, which this project does not currently do. Don't remove the rewriter without a replacement in place.
26. **`DrawGroup` applies the group's `OffsetX`/`OffsetY` as a `TranslateTransform`** before iterating children (`Canvas/RenderCanvas.cs:DrawGroup`). Without this, `PathAnimation`/`MoveAnimation` against a `VGroup` target had no visible effect — the animation set `group.OffsetX/Y` but the renderer drew children with only *their* offsets, ignoring the group's. The translation pushes screen units (`group.OffsetX * _viewport.Scale, -group.OffsetY * _viewport.Scale`); Y is negated because world Y-up vs screen Y-down. Don't move this into the child loop; the transform is a single push/pop wrapping the whole group.
27. **`new VPoint(...)` implicitly converts to `VXYZ`** (`C2VGeometry/Shapes/VPoint.cs`, `public static implicit operator VXYZ`). Backward-compat shim: pre-2026.5.5 projects whose canvas-drawn polygons/polylines/splines were serialized as `new VPolygon(new VPoint(...), ...)` still compile against the current `params VXYZ[]` constructors. New code should construct `VXYZ` directly because a `VPoint` constructor call auto-registers a drawable point marker on the canvas — the conversion fixes compilation but not the phantom-marker pollution. `CodeGenerator.GeneratePolygonConstructor`/`Polyline`/`Spline` and the editor's `vpoly`/`vbezier`/`vspline`/`vlinea`/`star`/`wave` snippets now emit `new VXYZ(...)` so the pollution never reappears in newly-generated code.
28. **Completion auto-trigger fires on space after `new`/`is`/`as` and on the first letter following them** (`Editor/SharedEditorController.OnTextEntered` + `IsAfterCompletionKeyword`). The previous rule waited until the *second* character of an identifier (caret-2 had to be a word char), so `new V` never popped the list — only `new Vc` would. Now the helper walks back over whitespace, pulls the preceding word, and triggers if it's a priming keyword. Shared `Editor/` source.
29. **`Region(ICurve closedCurve)` consumes its source curve** (`C2VGeometry/Shapes/Region.cs`). The single-closed-curve constructor (and the `AddHole(ICurve)` overload) build the loop via `BuildClosedLoop`: `VPolygon`/closed `VPolyline` decompose into **`VLine.Internal`** edges (non-registering — same anti-pollution rule as notes 6/10), while `VCircle`/`VEllipse`/closed `VSpline`/`VBezier` are stored whole as a single-element `OuterLoop` (the renderer and `Area`/`Perimeter`/`Contains` all sample non-`VLine` curves via `ICurve.Divide`, so a lone closed curve renders and measures correctly). After building the loop it calls `src.Remove()` on the source (the user-chosen "consume" behavior) so the curve isn't drawn twice. A non-circular/elliptical curve that is *open* (start != end) throws `ArgumentException`. Guarded by `Tests/RegionFromClosedCurveTests.cs` (in the `"CanvasState"` collection per note 9).
30. **Properties-panel "flex" sliders use a two-tier update: live preview during drag, single commit on release** (`PropertiesPanel.xaml.cs` → `BuildFlexSliderRow`). Each numeric geometry row gets a `[min] [slider] [max]` row. The catch: the normal commit path (`RaisePropertyChanged` → `MainWindow.OnPropertiesPanelPropertyChanged`) both redraws the canvas **and** rewrites the user's source via `CodeSyncManager.UpdateShapeCode` + resets `CodeEditor.Text` — doing that on every `ValueChanged` tick would flicker the editor, spam undo history, and jump the caret. So `Slider.ValueChanged` mutates the shape and fires the lightweight **`ShapeLivePreview`** event (MainWindow handler does *only* `RenderCanvas.Refresh()`), and the full `RaisePropertyChanged` commit happens once on `PreviewMouseUp`/`LostFocus` (guarded by a per-row `dirty` flag). Re-entrancy between the value TextBox and the slider is gated by the existing `_isUpdating` flag. The `GetGeometryProperties` descriptor is now a `GeoProp` (label, string `SetText`, numeric value, `SetNumber` that mutates *without* committing, `IsInteger`/`NonNegative`). **Don't route slider drags through `RaisePropertyChanged`.**
31. **Region boolean ops take collections, and `BooleanOps` forwards region calls to `RegionBooleanOps`** (`C2VGeometry/Operations/RegionBooleanOps.cs`, `BooleanOps.cs`). `RegionBooleanOps.Union/Intersect/Difference/Xor` each have `(IEnumerable<Region>)` and `(params Region[])` overloads that fold the binary op across all regions (Intersect = common to all; Difference = first minus the rest; Xor = running symmetric difference; implemented region-by-region since `PolygonClipper` has no native multi-subject call). `BooleanOps` (the VPolygon class) gained delegating `Region`/`IEnumerable<Region>` overloads so `BooleanOps.Union(listOfRegions)` resolves — but **no `params Region[]` on BooleanOps** (it would make the zero-arg `BooleanOps.Union()` ambiguous with the existing `params VPolygon[]`). Heads-up: `RegionBooleanOps`/`BooleanOps` fold collections region-by-region because the underlying `PolygonClipper` boolean call is binary (subject vs clip), not because of any geometry limitation.
32. **`PolygonClipper` (`C2VGeometry/Operations/PolygonClipper.cs`) delegates polygon booleans to the Clipper2 library** (`Clipper2` NuGet package, namespace `Clipper2Lib`), added to `C2VGeometry.csproj` and inherited transitively by every consumer (DoodleSharp, Tests). It replaced a hand-rolled Greiner-Hormann tracer that failed on degenerate inputs: a polygon **vertex landing exactly on another polygon's edge** (the reported bug — a circle centered on a rectangle's corner samples vertices onto the rect edges, so G-H found *zero* crossings and wrongly returned the regions as disjoint → `Union` gave `null`), and **full collinear shared-edge bands** (mis-unioned to one input). The Clipper2 path uses `ClipperD(precision: 8)` (double API, scales internally) + `FillRule.NonZero`, executes into a `PolyTreeD`, then `CollectOuterContours` (flat `Union/Intersect/Difference` — non-hole contours only, islands included) or `BuildPolygonsWithHoles` (`*WithHoles` variants — outer + immediate hole children). **`precision: 8` is Clipper2's maximum** (1e-8 grid) — raised from 6 so genuinely sub-micro geometry survives boolean ops instead of collapsing onto a 1e-6 grid; the trade-off is the largest safe coordinate drops from ~9.2e12 to ~9.2e10 (Clipper works in Int64; scaled coords must stay under 2^63−1), still far beyond any realistic canvas range. The matching vertex-stitching/overlap tolerance in `Region`/`VPolygon` (`ConnectionTolerance`) was tightened from `1e-6` to `GeometryTolerance.Epsilon` (`1e-9`) so distinct sub-micro vertices aren't merged when building loops. `Xor(VPolygon,VPolygon)` stays `(A−B)+(B−A)` so it returns hole-free pieces (the historical flat contract). **`PointInPolygonTest` is unchanged** — still the local ray-cast, used widely outside booleans. **`Clipper2Lib.dll` must ship**: the installer enumerates DLLs explicitly, so `installer.iss` has an explicit `Clipper2Lib.dll` line next to `C2VGeometry.dll`. Guarded by `BooleanOpsTests` (collinear-band, donut-with-hole, sub-micro Union/Intersect) and `RegionFromClosedCurveTests.Union_CircleCenteredOnRectangleCorner_MergesNonNull`.
33. **`VLine` exposes its endpoints only as `Start`/`End`; `VArrow` likewise.** Both used to carry a redundant pair — settable `Start`/`End` (`{ get; set; }`) plus read-only `StartPoint`/`EndPoint` aliases (`=> Start`). The aliases are gone. `VLine` still satisfies the `ICurve.StartPoint`/`EndPoint` contract via **explicit interface implementation** (`VXYZ ICurve.StartPoint => Start;`), so `vline.StartPoint` no longer resolves on a concrete `VLine` (use `.Start`/`.End`) but generic `ICurve` code keeps working unchanged — that's why `Region`/`VPolygon` loop-stitching (which goes through `ICurve`) was untouched while the concrete-`VLine` readers in `Region`, `VPolygon`, and `CurveIntersection` switched to `.Start`/`.End`. `VArrow` is a plain `Shape` (not `ICurve`), so its aliases were simply **deleted**, no explicit impl needed. The other 9 curve shapes never had the redundancy — they expose `StartPoint`/`EndPoint` only (computed from their own data), so they were not touched. **Don't reintroduce public `StartPoint`/`EndPoint` aliases on `VLine`/`VArrow`.** The settable `Start`/`End` is the canonical, ergonomic endpoint API; the core geometry math (`GeometryHelper`, `RayCaster`, `SpatialGrid`, `CurveIntersection`) already standardizes on it.
34. **`VPoint` arithmetic operators (`+ - * /`) all live in `VPoint.cs` and always return a plain `VXYZ`, never a `VPoint`.** C# only considers operators declared on the operand types, so `VXYZ`'s own operators are *not* candidates unless an operand is literally `VXYZ` — that's why `VPoint + VPoint`, `VPoint * scalar`, and `VXYZ * VPoint` failed to compile before (only `VXYZ ± VPoint` worked, via the implicit `VPoint→VXYZ` conversion from note 27). The fix adds the full set of overloads on `VPoint` covering VPoint⊕VPoint, VPoint⊕VXYZ (both orders), and scalar `*`/`/`. **They must return `VXYZ`, not `VPoint`** — a `VPoint` result would auto-register a phantom marker on the canvas for every intermediate (same anti-pollution rule as notes 6/10/27). Semantics: a `VPoint` participates as `(X, Y, 0)`; additive ops are full 3D component-wise (a `VXYZ` operand's Z passes through), multiplicative ops are computed in the XY-plane (Z = 0) — Hadamard for vector⊗vector — which also sidesteps divide-by-zero on the absent Z. Guarded by `Tests/VPointArithmeticTests.cs`.
36. **`VText` glyph→shape extraction uses an injected provider seam (`C2VGeometry/Interfaces/IGlyphOutlineProvider.cs`), because C2VGeometry is WPF-free and can't rasterize fonts.** `VText.GlyphOutlineProvider` (static, mirrors `Shape.DefaultRegistry`) is set by the app to `Canvas/GlyphOutlineProvider.cs` — a WPF impl using `FormattedText.BuildGeometry` + `GetFlattenedPathGeometry` that returns per-character contours in **world coordinates** matching `RenderCanvas.DrawText` (box top-left = `Location + anchorOffset` using `formattedText.Height` as the world box height — NOT `VText.Height`, which is what `GetBounds` uses, a pre-existing minor discrepancy; text-y-down flipped to world-y-up; CCW `Angle` applied around `Location`). Wired at `CanvasRenderer.Instance` (next to `DefaultRegistry`). `VText.ToCharShape(i)` (non-mutating), `LiftChar(i)`/indexer `this[i]` (extract **and** blank the char to a space), and `LiftChars(start,count)` build the result: a single-contour glyph → closed `VPolyline`; a glyph with holes → `VGroup` of contour polylines. Contour children are built under `AutoRegister=false` so only the returned shape registers (Chart-helper anti-pollution rule); the result is registered only if `AutoRegister` is on (TransformAnimation's `EnsureOnCanvas` covers the auto-draw-off case). `TransformAnimation.SampleOutline` was taught to morph a `VGroup` by sampling its **longest** child contour, so a lifted multi-contour glyph (`O`/`A`) morphs by its dominant outline. Returns null for whitespace / out-of-range / no provider.

37. **Global Parameters (`C2VGeometry/Parameters/`, `GlobalParametersPanel.xaml`, `Project/ParameterCodeWriter.cs`)** — a project-wide registry of named values (`GlobalParameters.Set/Get`) that survives across runs and is editable live from an F6 sidebar. **Reactivity is "re-run everything", not a dependency graph:** the registry lives in the *host* assembly so it outlives the collectible user ALC, and a value change simply re-executes `Main()` — every derived value is recomputed, no invalidation logic to get wrong. Key pieces:
    - **`ParamValue`** is a struct with implicit conversions to `double`/`bool`/`string`/`DateTime` so `Get("X") * 0.5` and `Get("Y") ? a : b` compile without a type argument. **`int`/`float` are deliberately *explicit*** — implicit ones would make `Get("n") * 2` ambiguous between `int*int` and `double*double`. The known cost: converting to both `double` and `string` makes **`+` ambiguous** (`double+double` vs `string+object`), so `Get("n") + 1` is a compile error; `.Num`/`.Text`/`Get<T>()` are the escape hatches. Don't "fix" this by dropping a conversion without re-reading that trade-off.
    - **Declare-vs-override is the crux.** `Set(...)` is an *idempotent declaration*: re-running must not clobber a value the user just dragged, or the slider snaps back every run. But a *changed literal* in code must win. Hence `Parameter.DefaultValue` + `IsOverridden`. `SetRange` sets `RangePinned` so a panel-widened slider range isn't undone by the next run's `min:`/`max:` args.
    - **`BeginRun()`/`EndRun(pruneStale)` wrap the `Main()` invoke** (`ModuleCompiler.InvokeMainAsync`). `BeginRun` suppresses `Changed` — **mandatory**, or the `Set(...)` calls inside `Main()` raise Changed → re-run → raise → unbounded loop. `EndRun` prunes parameters not re-declared this run (so deleting a `Set` line clears its panel row) but only when the run completed, so an error doesn't blank the panel.
    - **Resident-assembly fast path.** `ModuleCompiler` keeps the last successful `Main()` assembly + ALC loaded (`_residentContext`/`_residentMain`, `HasResidentAssembly`, `ReExecuteResidentAsync`, `InvalidateResident`). A parameter change doesn't touch source, so the IL is still valid — re-invoking is ~ms vs a few hundred for a Roslyn compile, which is what makes slider drags interactive. `ExecuteAssemblyAsync` invalidates the previous resident before loading a new one; any source write (including the panel's own write-back) calls `InvalidateResident()`. Caveat: static state in user code is *not* reset between resident re-runs.
    - **Two-tier panel updates** (same rule as note 30): slider `ValueChanged` → `Assign` → `Changed` → MainWindow's 40 ms timer → resident re-execute. The code write-back + full recompile happens **once**, on `ParameterCommitted`. **End-of-drag must be detected via `Thumb.DragStarted`/`DragCompleted`, not `PreviewMouseLeftButtonUp`** — while the Thumb holds mouse capture the button-up never reaches a handler on the Slider, so a drag ended with no commit and the edit never reached the source (verified in the live GUI). A 450 ms idle timer backstops gestures with no end event (wheel, track repeat-clicks), suppressed while `_isDragging`.
    - **Write-back** (`ParameterCodeWriter`) uses `[CallerFilePath]`/`[CallerLineNumber]` captured on `Set(...)`, so it *knows* the call site and only has to scan the argument list (bracket/string/comment aware) for the value argument. It replaces via `CodeEditor.Document.Replace` (surgical — preserves undo + caret; **don't** reset `CodeEditor.Text`) and reports a reason string when it can't find the call rather than failing silently. Date parameters are never written back (the declaring expression is usually `DateTime.Now`).
    - The panel ignores `Reloaded` while `_isDragging`, or the rebuild would tear the slider out from under the mouse.
    - DoodleSharp-only for now; `GlobalParameters` itself is WPF-free in `C2VGeometry` (namespace `C2VGeometry`, so `using C2VGeometry;` in the templates is enough), so another host could adopt it without library changes.

38. **Line weight / line type scale have an Absolute vs zoom-relative render mode, and all shape pens go through `RenderCanvas.GetShapePen()`** (`Canvas/RenderCanvas.cs`, settings `AppSettingsData.LineWeightRelativeToZoom`/`LineTypeScaleRelativeToZoom`, **both default `true`**). Absolute is the historical behaviour: `LineWeight` is device pixels and dash lengths are fixed on-screen, because the `DrawingContext` is never globally scaled — only per-shape geometry is multiplied by `_viewport.Scale`. Relative (the default) reinterprets the value as world units by multiplying by `_viewport.Scale`, so strokes and dashes scale with the drawing. Note the defaults are only defaults: an existing `appsettings.json` predating these keys deserializes without them and therefore picks up relative, but once a user touches either dropdown their choice is persisted and wins. **The subtlety is that WPF `DashStyle` lengths are multiples of the pen thickness**, so a zoom-relative *thickness* already stretches the dashes; `GetShapePen` divides that back out (`dashScale *= lineWeight / thickness`, using the *clamped* thickness so clamping doesn't distort the pattern) and multiplies in `zoom` separately when the dash mode is relative — each mode then applies exactly once, and all four combinations behave as advertised. Verified in the live GUI: relative weight at a zoomed-in view thickens strokes without changing dash lengths. Guards that must stay: thickness clamped to `[MinRelativeLineWeight, MaxRelativeLineWeight]` (a relative stroke would otherwise vanish zoomed out and swallow the canvas zoomed in), dash scale clamped to `[MinDashScale, MaxDashScale]` plus a `scale <= 0 → DashStyles.Solid` bail in `GetDashStyle` (zero-length dashes), and `GetCachedPen` rounds *both* thickness and scale into the key and clears `_scaledPenCache` past `MaxPenCacheEntries` — continuous zoom otherwise walks the key space and grows the cache without bound. **New shape draw methods must call `GetShapePen`, not `GetCachedPen`** (the chrome/overlay pens — grid, axes, snap markers, selection handles — are deliberately fixed-pixel and stay direct `new Pen(...)`).

39. **Auto Save lives entirely in `MainWindow` and reuses the existing save path** (`_autoSaveTimer`, `ApplyAutoSaveSettings`, `AutoSaveTimer_Tick`; settings `AutoSaveEnabled`/`AutoSaveIntervalSeconds`). The tick calls `SaveCurrentEditorContent()` then `VizCodeProject.SaveAllFiles()` — the same thing `Ctrl+S` does — so it inherits "only files with `HasUnsavedChanges` are written". Note the dirty flag is set by the `CodeEditor.TextChanged` handler, *not* by `SaveCurrentEditorContent()` (which only copies text), so the flush must come before the `HasUnsavedChanges` check. **The prompt path is the part with real invariants:** `ProjectNeedsSaveLocation()` treats a `ProjectDirectory` under `Path.GetTempPath()` as the "unsaved new project" state (there is no `ProjectFilePath == null` state — `CreateNew` always writes a `.vizproj` immediately) and also catches files with `IsNew`/empty `FilePath`, which `SaveAllFiles` would otherwise try to write to a non-existent path. A background timer that pops a modal every N seconds is a nightmare, so: `_autoSavePromptActive` blocks a second prompt while one is on screen, `_autoSavePromptSuppressed` goes up after a "No" and is cleared only when the project actually acquires a real path (checked on each tick, so it self-heals with no hooks into the many places `_currentProject` is assigned). `ApplyAutoSaveSettings` is null-safe and is called both when the timer is created and at the end of `LoadSettingsToUI`; the timer is stopped in `Window_Closing` so it can't fire a prompt during shutdown. Clamp the interval to `[MinAutoSaveSeconds, MaxAutoSaveSeconds]` rather than trusting the settings file.

40. **Crash journals live in `Diagnostics/` (`Journal`, `SystemSnapshot`, `AppDiagnostics`).** They write to `%TEMP%\DoodleSharp\YYYYMMDDhhmmss.log`, one file per process; the header names the app that wrote it. Full reference in **`docs/DIAGNOSTICS.md`**.
    - **The writer is synchronous and `AutoFlush = true` — do not "optimise" it into a background queue.** The whole point is that `StackOverflowException` / `AccessViolationException` / `FailFast` kill a .NET Core process with no handler running, so the only surviving evidence is what already reached the OS. A queued writer loses exactly the records that matter. `DOODLESHARP_JOURNAL_SYNC=1` upgrades to `FileOptions.WriteThrough` for machine-level crashes.
    - **Site keys must be unique across the repo.** `Tests/JournalSiteKeyTests.cs` scans every `.cs` file (excluding `bin`/`obj`/`Tests`/`Sample Projects`) for `Journal.<Method>("KEY"` / `Journal.Write(JournalLevel.X, "KEY"` and fails on a duplicate or a malformed key (`^[A-Z][A-Z0-9]*(\.[A-Z0-9_]+)+$`). That uniqueness is what lets a key in a user-submitted journal be grepped back to one line. **Because the scan keys off the `Journal.` prefix, the self-calls inside `Journal.cs` are written `Journal.Info(...)`, not bare `Info(...)`** — un-qualifying them silently drops them from the uniqueness guarantee. A third test (`CriticalPathsAreInstrumented`) pins the keys that must never disappear (`APP.STARTUP`, `PROJ.FILE.OPEN`, `MW.FILE.SELECT`, `EXEC.MAIN.INVOKE`, `CRASH.WPF.DISPATCHER`, `CRASH.APPDOMAIN`, `DIAG.UI.HANG`, `JRNL.HEARTBEAT`).
    - **`AppDiagnostics.Install(app, name, args)` must be the first statement in `App.OnStartup`** — before `base.OnStartup`, before any window — or a start-up crash goes unrecorded. It attaches `DispatcherUnhandledException`, `AppDomain.UnhandledException`, `TaskScheduler.UnobservedTaskException`, `FirstChanceException`, `AssemblyLoad`, `ProcessExit`/`Exit`/`SessionEnding`, and starts the UI-hang watchdog.
    - **Absence of `# SESSION END (clean)` *is* the crash signal.** `MarkCleanExit` writes it; the next launch tails recent journals for it and appends any that lack it to `crashes.txt`. Don't write that marker from anywhere but the shutdown path.
    - **First-chance tracing is bounded on purpose** (`FirstChanceGlobalCap`, per-site cap, `[ThreadStatic]` reentrancy guard). WPF and Roslyn throw-and-swallow constantly; unbounded logging would both bury the signal and cost real time on the throw path.
    - **`Journal.Activity(key)` is the per-frame API** — it increments an in-memory counter that the 10 s heartbeat summarises. Never call `Journal.Info` from a render/tick path. `RenderCanvas.RedrawAll` uses it.
    - **`RedrawAll` wraps the per-shape dispatch (`DispatchShapeDraw`) in a try/catch that logs `CANVAS.DRAW.THREW` with the shape's id/name/type/bounds and then *rethrows*.** Swallowing would leave the `DrawingContext` with unbalanced Push/Pop from a half-drawn `VGroup` and corrupt every later frame — the catch exists only to name the culprit, which the WPF crash stack cannot.
    - State providers (`Journal.RegisterStateProvider`) are invoked from every crash handler; the app's dumps the editor buffer via `Journal.WriteBlock`. Keep them cheap and exception-proof — they run while the process is dying.
    - `AssemblyInfo.cs` carries `[assembly: InternalsVisibleTo("DoodleSharp.Tests")]` so tests can call `Journal.ResetDirectoryCache()` alongside the `DOODLESHARP_JOURNAL_DIR` override.
    - **`AppDiagnostics` must not use WinForms** (`Screen.AllScreens` etc.) — screen geometry comes from `SystemParameters`, so the file stays portable to any host that doesn't set `UseWindowsForms`. Same reason `SystemSnapshot` uses `DllImport` rather than `LibraryImport` for `GetGuiResources`: the latter needs `<AllowUnsafeBlocks>`, which the project does not enable.

41. **`ModuleCompiler.CreateCompilationAsync(project, forExecution)` is offset-faithful by default; only the execute path rewrites source.** `forExecution: true` applies `AnimationNameRewriter` (injects `{ Name = "x" }` so `HideUnnamedShapes` can tell named from anonymous shapes) **and** `StackGuardRewriter` (note 21). Both insert text and therefore shift character offsets. Previously the name rewriter ran unconditionally, so every offset-based editor feature was reading a tree that did not match the editor: **F12 / Shift+F12 resolved the wrong token** in any file containing a named shape declaration ahead of the caret, and **rename wrote its edits at shifted offsets into other files** (`ApplyRefactoring` silently skipped the out-of-range ones, so it looked like a partial rename rather than corruption). The default is the safe one so a new caller that forgets the flag gets correct offsets instead of silent damage. Guarded by `Tests/EditorWorkspaceTests.cs` (`EditorCompilation_PreservesSourceOffsets` + `ExecutionCompilation_StillAppliesTheRewriters` — the second matters just as much, since dropping the rewriter from the run path would break shape naming and the stack guard).

42. **"Generate method" resolves its target from the semantic model, never by counting braces** (`Editor/RefactoringProvider.cs` → `ResolveGenerationTarget`/`FindMemberInsertionPoint`, `Editor/MethodStubBuilder.cs`, `MainWindow.GenerateMethodFromQuickAction`). The receiver decides everything: a type-name receiver (`VectorManager.DrawVector(...)`) means a `public static` member on **that type, in whatever file declares it**; a value receiver means an instance member on its type; no receiver means the enclosing type. The insertion point comes from `INamedTypeSymbol.DeclaringSyntaxReferences`, which is what makes cross-file generation work and what makes braces inside strings and comments harmless — the old implementation scanned backwards from EOF for the second `}` in the *active document*, so it could only ever write into the open tab and only landed correctly in a file holding exactly one type in one namespace. Two rules that are easy to regress:
    - **Insert at the start of the closing brace's line, not at the brace token.** The brace's indentation is *leading trivia*, so inserting at `CloseBraceToken.SpanStart` slides the stub between the indent and the brace — leaving a whitespace-only line and pulling the closing brace out to column 0. Verified in the live GUI. `FindMemberInsertionPoint` returns the line start when the brace owns its line, and otherwise (a one-liner like `class X { }`) returns the brace with `CloseBraceIndent` set so the stub re-emits what preceded it.
    - **Metadata types offer no action at all.** A member cannot be added to `C2VGeometry`/BCL/NuGet types, and falling back to the current class would generate something the call site cannot reach. `GenerationTarget.IsInSource == false` suppresses the action.
    - `MethodStubBuilder` exists so signature/indentation/placement are testable without a WPF editor; `Tests/RefactoringProviderTests.cs` covers targeting, staticness, accessibility, parameter inference, brace-in-comment robustness, indentation, and an end-to-end apply-then-recompile.

43. **The main window's editor is its own inlined implementation, not `SharedEditorController`** (see note 14) — so completion fixes have to be made in **both** places until that migration happens. Fixed in `MainWindow.xaml.cs`:
    - **Typing `.` while a completion list is open must close it first.** `TriggerManualCompletion` early-returns while `_completionWindow` is non-null, and the open list then filters itself to nothing and closes — so the member list never appeared. This is the single most common "suggestions don't show" report. `TextEntering` now closes the window and lets `TextEntered` re-trigger. **Do not trigger the dot from both handlers** — that starts two overlapping async queries and orphans one window.
    - **`_completionWindow` must only be published once the window is actually shown.** It is the busy gate every trigger checks; assigning it before `Show()` meant any exception in between left a non-null field for a window that would never open or close, killing IntelliSense for the rest of the session. `_completionRunning` covers the `await` in the same way. `ShowCompletionWindowWithSelection` clears the field on its empty-list early return.
    - **Auto-popup on typing** (second identifier character, or the first after `new`/`is`/`as`) and **commit-on-non-identifier-character** (`CompletionList.RequestInsertion`) — both were missing; only `.` and Ctrl+Space opened a list, and only Enter/Tab committed.
    - **The workspace must track the project's file set.** `SyncCompletionWorkspaceFiles()` is called after New File and after the file-watcher refresh, and `SelectFile` pushes the outgoing file's text before switching (semantic updates are debounced 500 ms). Files created mid-session used to stay invisible to completion until a project reload, and deleted files kept resolving forever (`CachedCompilationWorkspace.RemoveFile` had no call sites).

44. **Member-access completion classifies the receiver by symbol, not by `GetTypeInfo`** (`Editor/RoslynCompletionService.cs`). For a type name, `GetTypeInfo` *also* reports a type, so deciding "static or instance?" from it treats `VectorManager.` as an instance access and filters out precisely the static members being reached for. Check `GetSymbolInfo(...).Symbol is INamedTypeSymbol` first, then `INamespaceSymbol`, and only then fall back to `GetTypeInfo(...).Type`. Related rules in the same file: an **instance** receiver hides statics (except reduced extension methods and nested types); an **unbindable** receiver after a dot returns an empty list rather than falling through to the global lookup, which used to fill the list with locals and keywords that are not members of anything; and `ShouldHide` no longer suppresses `ToString`/`Equals`/`GetHashCode`/`GetType` or type parameters — hiding them everywhere, including on overriding types, read as broken IntelliSense. **A dot at the end of a line does not parse as a member access at all**: the parser swallows the *following* statement, so `circle.` above `Animation a = …` becomes the qualified **name** `circle.Animation`. In that shape `GetSymbolInfo` reports no symbol (it offers the real local under `CandidateSymbols`, `CandidateReason.NotATypeOrNamespace`) and — the part that made this silent — **`GetTypeInfo` returns a non-null *error* type**, so a plain `!= null` check concluded the receiver had bound and the member lookup ran against a type with no members. Hence: take a lone `CandidateSymbols[0]` when `Symbol` is null, **reject `ITypeSymbol { TypeKind: TypeKind.Error }`**, and only then fall back to `ResolveReceiverByName` (speculative binding of the receiver text at the dot). This is the "typed `circle.` and got nothing, not even with Ctrl+Space" report — and it fires on the *common* case, since a dot is normally typed with code already below it. Guarded by `Tests/CompletionServiceTests.cs`.

45. **`RefactoringProvider.Workspace` is the fast path for quick actions and navigation.** Without it every Ctrl+., F12 and Shift+F12 called `ModuleCompiler.CreateCompilationAsync`, which re-reads every file from disk, re-parses, and runs `GetProjectReferencesAndDllsAsync` — **a NuGet restore per package**, so right-clicking in a project with packages could block on the network. `MainWindow.InitializeCompletionWorkspace` assigns the editor's `CachedCompilationWorkspace`, which holds an incrementally-updated compilation over the same sources and is offset-faithful by construction. Note the workspace keys trees by **file name**, not full path, which is why every tree lookup in `RefactoringProvider` accepts a file-name match as well.

46. **`App.OnStartup` opens a `.vizproj` passed on the command line** (`App.xaml.cs`, `FindProjectArgument`/`TryOpenProject`). `installer.iss` has always registered the association (`[Registry]` → `shell\open\command` = `"{app}\DoodleSharp.exe" "%1"`, gated on the `associatevizproj` task) and `ChangesAssociations=yes`, but the app discarded `e.Args`, so a double-clicked project landed on the welcome screen. **A load failure must fall through to the welcome window** — returning without showing *any* window would leave a running process with no UI, since `ShutdownMode` is the default `OnLastWindowClose`. `App.xaml` has no `StartupUri` (same trap as note 17: adding one would create a second window). `FindProjectArgument` is `internal` for `Tests/AppStartupTests.cs` via the existing `InternalsVisibleTo`.

47. **`ShouldHide`'s BCL decluttering must never touch user-facing types** (`Editor/RoslynCompletionService.cs`). The heuristics there are tuned for `System.*` — hide all-uppercase names (interop: `ABI`, `MS`), hide names ≤2 chars, hide a hard-coded noise list — and they misfire badly on the geometry API: the all-caps rule alone was silently removing **`VXYZ`**, the core coordinate type, from every completion list, so `VXYZ p = new VX` offered only `VXLine`. `IsUserFacingType` now short-circuits the whole block for anything declared in source or living under `C2VGeometry`/`DoodleSharp`. **Any new filter added there goes *after* that guard.**

48. **Space must never commit a completion** (`Editor/CompletionInteraction.cs`, used by `MainWindow.TextArea_TextEntering`). The classic AvalonEdit idiom — commit on any non-identifier character — is wrong for C#: the list auto-opens while typing an identifier, and keywords are not symbols, so committing on the following space rewrote what the user typed (`new ` → `VXYZ `, `new VXYZ(10, ` → `new VXYZ(10,Viz )`). `Commits()` is the explicit set `( [ { ; , )`; space closes the list and, after a priming keyword, reopens it. The rules are a separate pure class specifically so they are testable (`Tests/CompletionInteractionTests.cs`) — getting them wrong corrupts the user's text rather than merely being unhelpful.

49. **Completion has to work in half-written code.** Two rules follow from that:
    - **Open the window on `symbols + snippets`, not on symbols alone.** `TriggerManualCompletion` used to bail when Roslyn resolved nothing, which is exactly the state a half-typed `for` is in — so the `for` snippet was unreachable at the only moment it was wanted.
    - **Keywords are injected by `AddKeywords`** because `LookupSymbols` returns declared symbols only. Without them `for (int` fuzzy-matched type names and ranked `IntersectionResult` first, one commit character from insertion. Only in statement position — never after `.` or `new`.
    - `IsDeclaringAName` suppresses the list entirely when the caret is on the identifier of a declaration (variable, parameter, foreach element, method, type, property): naming something new is not a lookup, and a stray commit character would overwrite it.

50. **Signature help lists the whole overload set.** `SymbolInfo.Symbol` is populated only when the call already binds, and `CandidateSymbols` only when it does *not* — so the old code showed one signature for working code and the full list for broken code, which is backwards. `GetSignatureHelpInternalAsync` expands the resolved symbol to its siblings (`ContainingType.InstanceConstructors` for a ctor, `GetMembers(name)` otherwise), keeps the resolved one first, then orders by arity. There is also a workspace overload so methods in *other* project files resolve — the single-file path only sees the active tab. Note `Accessibility` must be fully qualified as `Microsoft.CodeAnalysis.Accessibility` here: `UseWindowsForms` pulls in a colliding COM namespace.

51. **Diagnostics are frequently zero-width, and must still be underlined** (`Editor/DiagnosticRange.cs`, used by `MainWindow.PerformSyntaxCheckAsync` and both Run-path marker loops). Roslyn reports every "missing token" error — a dropped `;`, `)`, `(`, an incomplete expression — as an **empty span** at the insertion point. The marker loops all guarded on `if (length > 0)` before creating a marker *or* incrementing the error count, so the most common class of mistake-while-typing produced no squiggle and a count of zero: a bare `for` yields **seven** diagnostics, every one of them zero-width, and the file read as clean. `DiagnosticRange.TryResolve` widens an empty span — forward over an identifier, else backward over the token just typed (the usual case, since the missing token belongs *after* it), else one character, never the line break. Two rules to keep: **count errors independently of whether a marker could be drawn**, and **merge diagnostics that resolve to the same range** or a single typo stacks seven overlapping squiggles with seven tooltips. Tested in `Tests/DiagnosticRangeTests.cs`, including an end-to-end case that feeds real compiler output through the resolver.

52. **Known gap — `RefreshFilesFromDisk` does not re-read already-open files.** It adds files new to the project and drops files deleted from disk, but leaves the `Content` of existing `VizCodeFile`s untouched, and `RefreshProjectFromDisk` only calls `SelectFile` when the active file object changed (it never does, since the object is reused). So an external edit to a file that is already open is silently ignored even though the status bar says "Project refreshed from disk". Fixing it needs a conflict policy for files with unsaved changes, which is why it is recorded here rather than patched. It also means external-edit-driven testing of the editor does not work — drive the UI instead.

53. **Overload sets must not collide once defaults are applied.** `VGrid` had `(VXYZ,int,int,double xSpacing=1.0,double ySpacing=1.0,bool centered=true)` alongside `(VXYZ,int,int,double spacing,bool centered=true)`; a four-argument call matched both, so **the uniform-spacing constructor was unreachable** (CS0121) and callers had to pass `centered` just to compile. Fixed by making `ySpacing` a `double?` that means "same as xSpacing" — so `new VGrid(loc,5,5,10)` is a square grid, which is what a reader expects — and by **removing the default on the uniform overload's `centered`**, which is what keeps it out of the four-argument case. Guarded by `Tests/VGridConstructorTests.cs`, which is as much a compile-time check as a runtime one.

54. **Every geometric shape must override `Contains` *and* `DistanceTo`; the `Shape` base versions are bounding-box stubs.** `Shape.DistanceTo` measures to the bbox *centre* and `Shape.Contains` tests the bbox — silently, confidently wrong for anything with a real outline: `new VLine(0,0,100,100).Contains(new VXYZ(100,0))` was **true**, and a point exactly on a circle reported a distance equal to its radius. `Operations/CurveGeometry.cs` holds the shared maths (`DistanceToSegment`, `DistanceToPath`, `DistanceToCurve` by sampling, `IsOnStroke` with a size-relative tolerance).
    - **The two must be overridden together.** This shipped broken twice: first `VLine` and friends had neither, then `VCircle`/`VHatch`/`Region` were found with an exact `Contains` still paired with the bbox `DistanceTo`. `Tests/ShapeOverrideConsistencyTests.cs` now enforces it by reflection over every public concrete `Shape`, with a justified exemption list (`VPoint`, `VText`, `VGroup`, `VGrid`, `VSpatialGrid`, `VDimension`, `VRadialDimension`, `VArrow` — the box really is the answer, or there is no outline). **A new shape either implements both or is added to that list with a reason.** The guard immediately caught `VRay`/`VXLine` when it was written.
    - **Semantics:** open curves — "on the stroke"; closed shapes (`VPolygon`, `VCircle`, full `VEllipse`, `VHatch`, `Region`) — a genuine interior test for `Contains`, and distance to the *boundary* for `DistanceTo` (positive both inside and out, not a signed depth). A partial `VEllipse` sweep encloses nothing and is treated as an open curve.
    - **`VArc` and `VCircle` compute distance exactly, not by sampling.** Chords sit inside the true arc, which put the centre-to-arc distance at 9.9987 instead of 10. `VXLine` is perpendicular distance with no clamping (it extends both ways); `VRay` clamps at its `Origin` only.
    - **`Region.DistanceTo` measures hole edges too**, so it stays consistent with `Contains`, which already excludes holes — otherwise a point just inside a hole reports itself as far from the boundary when it is sitting on one.
    - **`VHatch.Contains` uses `PolygonClipper.PointInPolygonTest`** like every other area shape; it used to carry a private crossing-number copy that could disagree on boundary-exact points.
    - The guard's exemption lists are **per method and deliberately different** — `VGrid`/`VSpatialGrid`/`VPoint` enclose no area (no `Contains`) but do have a meaningful nearest distance, so exempting them from both would let a real regression through. A fourth test asserts an exemption is never claimed for a shape that actually implements the method, which is how `VGroup` was found wrongly listed.
    - `SelectionTool` has its own `HitTestShape` with a pixel tolerance and does *not* use these, so click-to-select was unaffected throughout.
    - **Known limitation:** `VEllipse.Contains`'s implicit-equation test assumes the ellipse is axis-aligned, which it is — there is no rotation property. Adding one silently invalidates it.

55. **`Shape.RotationAngle` is `virtual`; `VRectangle` overrides it.** It used to `new`-shadow it, and the two members never met: the renderer holds a `VRectangle` and read the intrinsic angle, while `RotateAnimation` holds a `Shape` and wrote the animation one — so **rotation animations on rectangles silently did nothing**, and the meaning of `rect.RotationAngle` depended on the static type of the variable holding it. The override rebuilds the four corners about the rectangle's centre. **Never reintroduce a `new` member for this**; if another shape needs to rotate by rebuilding geometry, override too.

56. **`VEllipse` is arc-length parameterised, like every other `ICurve`.** `Evaluate(t)` used to interpolate the sweep *angle*, which is not the same thing on an eccentric ellipse — equal angles cover less arc near the flat ends, so `Divide(n)` bunched points there and anything sampling the curve evenly (dashes, animation paths, morph targets) inherited the distortion. It now walks a cumulative arc-length table (256 samples, memoised on radii + angles, so `Divide`'s loop builds it once). `EvaluateByAngle` keeps the old behaviour where it is genuinely wanted, and **`SetBounds` trims by arc length too** so the two agree.

57. **`GeometryDiagnostics.Sink` is how the geometry library talks to the user.** C2VGeometry is UI-free and was calling `System.Console.WriteLine` to explain why e.g. `BooleanOps.Union` returned null — which in a WPF process goes nowhere, so the user just saw null. The host assigns the sink at start-up alongside the other seams (`CanvasRenderer.Instance`). Null sink = silent and free; a throwing sink is swallowed, because diagnostics must never break the operation.

58. **`BuiltInHatches.Get` returns a `Clone()`, not the cached instance.** The cache holds one parsed `HatchType` per pattern; handing that out meant mutating a returned pattern's angle or spacing **poisoned every later lookup of that name for the rest of the session**. `HatchType.Clone()`/`HatchPatternLine.Clone()` are deep (the dash array is copied too).

59. **Anything computed asynchronously must re-check the caret before it is shown.** Both popups are built behind an `await` (Roslyn compile), and the user keeps typing during it — so the state the result describes is not necessarily the state on screen when it arrives. Two guards in `MainWindow`:
    - `TriggerCompletion(autoTrigger)` returns if `CodeEditor.CaretOffset != offset` **when the trigger was automatic** (a manual Ctrl+Space is an explicit request and still opens at its original position), and returns when the list came back empty — that second check is also what stops snippets from appearing while the user is naming a new variable, since `IsDeclaringAName` (note 49) empties the symbol list but the snippet list is built independently.
    - `ShowSignatureHelp` returns unless the caret is still at `offset` **and** `IsCaretInsideArgumentList()` — a bracket scan that stops at `;`, `{`, `}` or a newline. Without it the tooltip stayed up after the closing paren and the semicolon: the popup was requested mid-call and simply had nothing telling it the call had ended. `Caret_PositionChanged` closes it on the same test, so moving away dismisses it too. **Argument-list membership is a caret test, not an event-ordering trick** — don't try to fix this by only closing on the `)` keystroke, because the caret also leaves by arrow key, click, undo and Enter.

60. **Canvas delete must find the declaration with a balanced scan, and say so when it cannot** (`Canvas/CodeSyncManager.cs`, `MainWindow.DeleteSelectedShapes`). The declaration used to be matched with `new VRay\([^)]*\)` — an argument list of "anything but a closing paren", which **cannot span a nested call**, so `new VRay(p1, new VXYZ(1, 2))` never matched. Nested constructor arguments are the norm in this API, so deleting a shape routinely removed it from the canvas, reported "Deleted 1 shape", left the code untouched, and the shape came back on the next run. Now `GetShapePatterns` matches only up to the opening paren and the statement extent comes from `FindStatementEnd`, the shared scanner — which had to learn about strings, chars, and both comment forms, or a `;` inside a string literal truncated the file mid-statement. Three further rules on the host side: **flush the editor first** (`SaveCurrentEditorContent`) since the declaration may have been edited since the last run; **search every file**, not just the entry point, because a shape can be constructed in any module; and when a shape's code is not found, **say it in the status bar and journal it** rather than reporting a clean delete. Guarded by `Tests/CodeSyncDeleteTests.cs`.

61. **Rotation angles are degrees everywhere except `VTransform.CreateRotation`.** `Shape.Rotate`, `VXYZ.Rotate`, `VCoordinateSystem.Rotate`, `GeometryHelper.RotatePoint` and the `VArc`/`VEllipse` angle properties all take degrees; `CreateRotation` feeds its argument straight to `Math.Cos`/`Math.Sin` and is therefore radians. `VCoordinateSystem.Rotate(axis, angleDegrees)` **used to pass its degrees into it unconverted**, so a "quarter turn" of 90 rotated by 90 radians (~237°) — the parameter name promised degrees, so nothing could have depended on that deliberately, and it now converts. `CreateRotation` itself was left in radians on purpose (flipping it would silently break user code already passing `Math.PI / 2`); its parameter is named `angleRadians`, it carries an XML doc saying it is the odd one out, and `CreateRotationDegrees` is the wrapper for the library's usual convention. Guarded by `Tests/RotationAngleUnitTests.cs`, which includes a cross-check that `VCoordinateSystem.Rotate(BasisZ, θ)` agrees with `VXYZ.Rotate(θ)` — the two APIs a user is most likely to mix. **If you add a rotation API, it takes degrees.**

62. **The documentation surfaces have repeatedly documented API that does not exist**, and the only thing that catches it is a systematic pass by the `docs-author` agent against the real public surface (reflection over the built `C2VGeometry.dll`, then every `Type.Member` mentioned in the docs checked back against that dump). The 2026.8.5 pass found an entire fabricated `DoubleExtensions` class with `ToRadians()`/`ToDegrees()`, all nine documented `GeometryHelper` members, every documented member of `VPlane`/`VCoordinateSystem`/`VTransform`, `VCircle.Diameter`, `VPolyline.PointCount`, `Shape.CopyStyleTo`, and `PolygonClipper` (which is `internal`) presented as the public escape hatch — several with runnable F1 samples that could not compile. This is why the pass is a **required** release gate rather than an optional polish step: read the signature before writing an example.

63. **`RefreshFilesFromDisk` re-reads open files, and reports what it actually did** (`Project/VizCodeProject.cs`, `MainWindow.RefreshProjectFromDisk`). It used to add and remove files but never refresh the `Content` of one already open, so an external edit — another editor, a git checkout, a tool — was silently ignored while the status bar said "Project refreshed from disk". It now returns a `DiskRefreshResult` (`Added`/`Removed`/`Reloaded`/`Conflicted`/`Unreadable`) and the host reports the truth. The invariants:
    - **A file with unsaved changes is never overwritten.** It goes in `Conflicted` and keeps the in-memory text. A background watcher tick silently discarding what someone typed is the worst possible outcome, and a modal prompt from a timer is barely better (same reasoning as note 39) — so the resolution is a status message telling them how to choose.
    - **Identical content is a no-op, not a reload.** Our own `SaveAllFiles` trips the watcher, so "nothing changed" is the *common* path; rewriting the buffer would reset the editor and jump the caret on every Ctrl+S. `ReportDiskRefresh` also stays silent in that case rather than clobbering the status bar.
    - **The editor keeps its caret and scroll** across a reload (`ReplaceEditorTextPreservingPosition`) — assigning `CodeEditor.Text` sends the caret to 0 and scrolls to the top, which is jarring when it happens to someone who was only reading. Wrap it in `_suppressUnsavedMarking` or the reload marks the file dirty.
    - **Reads retry briefly on `IOException`** (`TryReadFile`, 3 × 60 ms): the watcher fires while the writer still holds the handle, and a single failed attempt loses the change permanently because nothing fires again.
    - Guarded by `Tests/DiskRefreshTests.cs`, which drives real files in a temp directory.

64. **Query methods must not draw their answer.** `GeometryHelper.IntersectLineLine`/`IntersectRectRect`/`IntersectLineRect` return a `Shape?` because the answer's *kind* varies (a crossing is a `VPoint`, an overlap a `VLine`), and `VRay.ToFiniteLine`/`ToXLine` and `VXLine.ToFiniteLine` convert "for intersection calculations" — every one of them auto-registered, so asking a question littered the canvas. This is the note 6/10/27 pollution rule reaching public API. They now build their result under **`Shape.SuspendAutoRegistration()`** (an `internal` `IDisposable` scope on `Shape` that restores the previous value rather than forcing `true`, so it nests safely inside the Chart helper's existing flip), and the XML docs tell the caller to `Draw()` the result if they want it visible. `VLine.Internal` is still preferred where the type is known. **The scope is not for hot paths** — the flag is process-wide, so a shape constructed on another thread inside the scope silently fails to register; it is fine for one-shot user-facing calls, not for loops. Same fix applied to `Region.CloneCurve`/`ReverseCurve`, which build a region's internal loop: `Clone()` is abstract and every implementation registers, so cloning a region leaked one shape per edge. Guarded by `Tests/GeometryRegistryPollutionTests.cs`, and `C2VGeometry.csproj` now carries `InternalsVisibleTo("DoodleSharp.Tests")` so those guards can assert on the internals directly.

65. **Canvas delete is undoable as one step, through `TransactionManager`** (`Commands/ShapeCommands.cs` → `DeleteShapesWithCodeCommand`, `MainWindow.DeleteSelectedShapes`). The command stack, `DeleteShapesCommand` and the Ctrl+Z routing all already existed; the canvas delete simply never pushed a command, so the one operation that **edits the user's source** was the one with no undo. Points that matter:
    - **Undo must restore the code, not just the shape.** Restoring only the shape leaves a drawing the next run silently undoes. The command captures each file's text verbatim **before and after** rather than re-deriving it — the edit is a text removal, and running the matcher backwards is not something that can be made reliable.
    - **A shape lives in two collections** — `CanvasRenderer` (the registry, what `RayCaster` and the run machinery see) and `RenderCanvas` (what is displayed). The old delete only touched the display list, so the shape lingered in the registry. Both are updated in both directions; `CanvasRenderer.AddShape` early-returns on `IsPlaced`, which `RemoveShape` clears, so the pair is symmetric.
    - **The write-back goes through one callback** (`ApplyFileContentFromCommand`) used by the original edit, the undo and the redo alike — duplicating it inside the command is how undo ends up subtly different from the thing it reverses. It also calls **`ModuleCompiler.InvalidateResident()`**, which the old delete did not: without it a Global Parameters change re-executes the stale IL and puts the deleted shape straight back (note 37).
    - **`IsCanvasUndoContext()` mirrors the Delete key's gate** (`!CodeEditor.IsKeyboardFocusWithin && !IsTextInputFocused()`) so anywhere you can delete, you can undo. The previous test — canvas focused, or moused over, or something selected — failed in exactly the state that matters: immediately after a delete, which clears the selection.
    - The multi-file search is lifted into `CodeSyncManager.PlanDeletion<T>` so it is testable without WPF: every file is searched, each shape stops being searched for once found (or one delete guts an unrelated file reusing the variable name), and shapes never found are returned for reporting. Guarded by `Tests/CodeSyncDeleteTests.cs`.
    - **The undo entry has to survive the run the delete itself causes** — this is what still made undo look broken after the command was added, and it is the subtle part. Every run site called `TransactionManager.Instance.Clear()`, reasoning that a run regenerates every shape from code so any command holding a `Shape` reference is stale. True of move/resize/style. But the delete **edits the source**, and writing that text back into the editor starts the debounced auto-run (`AutoUpdateCanvas`, **on by default**, 500 ms) — so the run *triggered by the delete* cleared the entry the delete had just pushed, and Ctrl+Z half a second later said "Nothing to undo". Pressing F5 after a delete lost it the same way. `ICommand.SurvivesCodeRun` (default interface member, defaulting to **`false`** so a forgetful new command is dropped rather than left dangling) marks the commands whose undo is fundamentally a source edit; `TransactionManager.PruneAfterCodeRun()` replaces `Clear()` at the three run sites and keeps only those, order-preserved, in **both** stacks. `CompositeCommand` survives only if every child does. **Don't put `Clear()` back on the run path** — `ClearButton_Click` still calls it, which is correct, because clearing the canvas is an explicit wipe. Note the two suppression flags are *not* the same: `_suppressUnsavedMarking` (set by `ReplaceEditorTextPreservingPosition`) stops the dirty-marking `TextChanged` handler but **not** the auto-update one, which is gated on `_suppressAutoUpdate`. Guarded by `Tests/UndoSurvivesRunTests.cs`.
    - Known limitation: undo re-appends restored shapes, so **z-order is not preserved** across an undo. The pre-existing `DeleteShapesCommand` has the same behaviour. Likewise **redo** after an intervening run removes shape objects the run has already replaced, so the shape stays visible until the code edit is picked up (immediately with auto-update on, at the next run without it); undo, the direction that matters, is correct either way.

66. **`Shape.Place()` is the name; `Draw()` is the historical alias.** `Draw()` had drifted into meaning two different things depending on the shape's state — "mark as explicitly drawn" on a registered shape (so the post-`Main()` unnamed-shape sweep spares it, the advice for boolean/array results) versus "actually put it on the canvas" on an unregistered one (query results per note 64, or anything built while `AutoRegister` was off). Both are the same two lines of code; only the starting state differed, so the fix was a name, not a behaviour: `Place()` sets `IsExplicitlyDrawn` and registers, `Draw()` is `=> Place()`. **Do not let them diverge** — `Tests/NewConvenienceApiTests.DrawIsExactlyPlace` pins the equivalence, because if they ever differ every existing sample and user project silently changes behaviour. `Draw()` is *not* `[Obsolete]`: a build warning on every existing call is a worse outcome than an extra name. **`IDrawable` declares `Place()` too**, as a *default* interface implementation (`void Place() => Draw();`) — `CanvasRenderer.GetShapes()` hands back `IDrawable`, so without it "prefer `Place()`" would fail to compile in exactly the place the documentation sends people; the default form means adding it cannot break an outside implementer. `Shape` implements `Place()` outright, so every reference type reaches the same method. **`Canvas/CodeGenerator.cs` and `Editor/CodeSnippets.cs` emit `Place()`** — the app is the largest producer of DoodleSharp source and was going to keep teaching the old spelling; `Tests/CodeGeneratorTests.cs` guards all twelve generated shape types plus an end-to-end generate-then-delete case, since the generator's spelling has to stay compatible with what `CodeSyncManager`'s delete matcher sweeps (a generic `varName.\w+.*;`, so both spellings work — but the test is what keeps that true).

67. **The four "documented but never implemented" conveniences now exist** — `DoubleExtensions.ToRadians()`/`ToDegrees()` (new, `C2VGeometry/Core/DoubleExtensions.cs`, framed as the boundary with `System.Math` since the library is degrees throughout), `VCircle.Diameter` (get/set, resizes about the centre), `VPolyline.PointCount` (null-safe `Points?.Count ?? 0`), and `Shape.CopyStyleTo`. Note **`CopyStyleTo` was not missing** — it existed as a `protected` helper for `Clone()` implementations, which is exactly why the docs agent's reflection dump reported it as not-public-API; it was promoted to `public`, made null-safe and self-safe, and now returns `target` for chaining. The relevant lesson: "documented but does not exist" and "documented but not reachable" look identical from the docs side and need different fixes. Guarded by `Tests/NewConvenienceApiTests.cs`. The `VCircle` factories are `FromCenterDiameter`, **not** `ByDiameter`.

68. **Animated rotation is applied once, in `RenderCanvas.DispatchShapeDraw` — never per shape.** `RotateAnimation` writes `Shape.RotationAngle`/`RotationPivot` on *any* `Shape`, but only `DrawLine`, `DrawCircle` and `DrawArrow` ever read them back, so **rotating an ellipse, arc, polygon, polyline, bezier, spline, text, group, hatch or region silently did nothing**. Note 55 fixed the same bug for `VRectangle` alone, which is exactly what made the general case easy to miss: per-shape opt-in meant fifteen `Draw*` methods simply never implemented it and nothing failed when they didn't. The transform is now pushed once around the whole dispatch, in a `try`/`finally` so a throwing `Draw*` cannot leave the `DrawingContext` unbalanced (note 40). **`VRectangle` is the one exclusion** — its `RotationAngle` setter rebuilds the corner geometry, so it arrives already rotated and a transform on top would rotate it twice; the dead identity-rotation branch that used to sit in `DrawRectangle` (unreachable, since a non-zero angle returns early) is gone. `Tests/ShapeRotationTests.cs` guards both the animation contract and, by scanning `RenderCanvas.cs`, that exactly one `RotateTransform(...RotationAngle...)` site exists. **`VText.Angle` is a different, intrinsic property and is deliberately not part of this.** Note that `RotationAngle` is a *render-time* transform: `Contains`, `DistanceTo` and click hit-testing all still work on unrotated geometry, which was true before this change too and is unchanged by it.

69. **Renderer changes can be verified visually, offscreen.** `RenderCanvas.Render(IEnumerable<IDrawable>)` is public, so a tiny WPF console app can instantiate the canvas, render a scene to a `RenderTargetBitmap` and write a PNG that can simply be looked at — which is how the rotation fix above was confirmed across every shape type. The recipe, since it has a few non-obvious requirements: build it **outside the repository** (a second `Main()` under the project root breaks DoodleSharp's build with a duplicate entry point — same trap as notes 12 and 22); mark `Main` `[STAThread]`; set `Shape.DefaultRegistry = CanvasRenderer.Instance` as the app does at startup or nothing registers; `Measure`/`Arrange`/`UpdateLayout` the canvas before rendering; composite the canvas over an opaque rectangle via a `VisualBrush` (it paints no background of its own, so the PNG is otherwise transparent); and alias `Size`/`Color` to the `System.Windows` versions because `UseWindowsForms` drags in the colliding `System.Drawing` types. This closes a long-standing gap — GUI behaviour previously could not be checked at all once synthetic input was refused.

70. **`VTransform.CreateRotation` is `[Obsolete]`; the names are now explicit.** `CreateRotationRadians` is the implementation, `CreateRotationDegrees` wraps it for the library's usual convention, and the original ambiguous name forwards to the radians one with a deprecation message. **The name is retired, not redefined** — redefining it to mean degrees would leave every existing call compiling and silently rotating by 1/57th of what it used to, which is precisely the failure that produced the `VCoordinateSystem.Rotate` bug (note 61). Nothing in the repo calls the obsolete overload, so no build warns; a user who does gets a message naming both replacements.

71. **`BooleanOps.UnionAll` returns every piece.** `Union` insists on a single polygon and returns null when the inputs do not all overlap or touch, which left no public way to union a set of separate shapes and see the result — the diagnostic used to point at `UnionWithHoles`, which only takes two polygons. `UnionAll` folds pairwise (the underlying clipper call is binary, note 31), absorbing every existing piece the new polygon touches and keeping the rest separate, so a chain that only connects through a third polygon still collapses to one piece. Guarded by `Tests/UnionAllTests.cs`.


73. **`VPolygon.Slice` cuts via two half-plane intersections through `PolygonClipper`, not by walking the perimeter.** The old implementation paired intersections in **perimeter order** and closed each piece with a single chord, which assumes every output piece is *one boundary arc plus one chord*. That holds only for a convex cut with exactly two crossings. A concave polygon whose notch straddles the line is crossed **four** times: the walker emitted the arcs between intersections 0-1 and 2-3, silently discarded arcs 1-2 and 3-0, and **could not represent the remaining piece at all** — that one is bounded by *two* arcs. The reported parcel came back as two slivers totalling 12,945 against an area of 225,561: **94% of the area vanished**, and because each sliver was a plausible-looking polygon nothing failed loudly. `Slice` now intersects the polygon with a large rectangle on each side of the line (`BuildHalfPlanes`) and concatenates the results, so it is area-preserving by construction and a four-crossing cut correctly returns three pieces. Same reasoning as note 32 — degenerate configurations belong in Clipper2, not in a bespoke tracer. Rules that must hold: **the half-plane rectangles are built under `Shape.SuspendAutoRegistration()`** (note 64) or every slice drops two enormous phantom rectangles on the canvas; their extent is measured **from the line's origin, not the polygon's own size**, because the two defining points may sit far outside the polygon; and **fewer than two pieces means the line never separated anything** (it missed, or grazed a vertex or a whole edge), so the documented contract of returning a clone of the original is honoured rather than a re-traced copy. `FindSliceIntersections`/`BuildSlicedPolygons`/`BuildSlicedPolygonsGeneral` are deleted — don't reintroduce a perimeter walker. Guarded by `Tests/PolygonSliceTests.cs`, which includes the reported parcel verbatim and asserts the pieces sum back to `Area` in every case. Historical note: `Slice(xline)`/`Slice(ray)` were advertised in places but have never existed — when auditing API claims, grep description strings and not just prose.


74. **`Rendering/SceneIndex.cs` is the culling structure; the `Canvas/SpatialIndex.cs` QuadTree is no longer on the render path.** SoA world bounds + a coarse uniform grid (CSR: one `_cellStart` offsets array, one packed `_cellItems`) + a `ulong[]` visibility bitset. Three things about it are load-bearing:
    - **A shape is entered into every cell its box overlaps, not just the one holding a corner.** The first benchmark run examined **9,844 shapes to draw 45**, because corner-binning sent anything wider than a cell to the always-scanned oversize list — and in a street grid half the shapes are exactly one block long, a hair over the cell size. Multi-cell binning made the same query consider **73**. The duplication is deduplicated for free by the visibility bitset, and by a per-slot query stamp for the list-returning path. Only shapes covering more than `MaxCellsPerShape` (32) still go to `_oversize`.
    - **Z-order comes out of the bitset, not a sort.** The slot index *is* draw order (the scene appends in order), so walking set bits ascending is already correct; sorting 100k indices per frame would cost more than the cull saves. `VisibleTopDown` walks them descending for hit-testing, where topmost-first is what picks the shape the user clicked.
    - **`VRay` and `VXLine` are unbounded by type, not by measurement.** Their `GetBounds()` returns a finite box from `RenderExtent` (10,000 units), but `DrawXLine`/`DrawRay` extend them across the *visible viewport*. Culling on that box makes an infinite construction line vanish once you pan past its extent. They are classified always-visible explicitly; a shape whose `GetBounds()` throws degrades to the same rather than taking the frame down.

    `QueryInto` exists separately from `Query` so snapping and hit-testing — which run from mouse-move, interleaved with rendering — cannot disturb the bitset the renderer culls with. Don't merge them. Guarded by `Tests/SceneIndexTests.cs`, which cross-checks queries against a brute-force scan rather than hand-picked expectations, and asserts the query path allocates **zero** bytes.

75. **Culling is no longer switched off during animation, and the frame no longer iterates every shape.** Both were in the original `RedrawAll`: a `HashSet<IDrawable>` was allocated per frame and then `foreach (_currentShapes)` walked all *n* probing it — so the index saved the *draw* but never the *iteration* — and culling was disabled outright whenever a timeline or sketch was playing, i.e. the only two 60 Hz paths. The answer for moving shapes is to re-index, not to draw everything: `RenderCanvas.ReindexForAnimationFrame()` is called from the timeline branch of the frame loop, because `Timeline.Update` mutates `OffsetX`/`OffsetY`/`DrawFactor` in place — the shape objects are identical and only their cached boxes are stale.

76. **Sketch mode used to render frame 0 forever.** `SketchRuntime.Tick()` calls `CanvasRenderer.Clear()` and re-runs the user's `Draw()`, so every frame produces *new shape objects* — but `RenderCanvas._currentShapes` is a `ToList()` snapshot assigned only by `Render()`, which the sketch path never called; the frame loop called `Refresh()` alone. A sketch that *created* its shapes in `Draw()` was frozen, and the default template does exactly that ("Fresh shapes each frame"). `SetFrameShapes` pushes the current registry contents before the repaint. Ordering matters — `Refresh()` paints whatever `_currentShapes` holds at the moment it is called. Guarded by `Tests/SketchFrameShapesTests.cs`.

77. **`Shape.Revision` is the cache-invalidation seam, and `VHatch`/`Region` use it.** Derived data — generated hatch segments, sampled region loops — is memoised against it. The measured reason: on a scene of ~15k shapes with a few hundred hatches, regenerating per frame cost **11.5 ms and 146 MB of allocation per frame**, with ~5,000 gen-0 collections over a 600-frame path; the hatches alone were two orders of magnitude more expensive than 100,000 lines. `VHatch.GetCachedLines()` and `Region.GetCachedOutline()` return **shared lists that must not be modified** — copying would reintroduce most of the allocation. `GenerateLines()` still returns a copy, so the public contract is unchanged. **Honest limitation:** `Revision` tracks *assignment*, not mutation, so editing `VPolygon.Points` in place leaves a cache stale; `Shape.Invalidate()` is the documented escape hatch until vertex collections are encapsulated.

78. **Level of detail is what bounds frame cost once culling has stopped helping** (`Rendering/LodPolicy.cs`). Culling answers *which* shapes are in view; zoomed out over a large drawing the answer is "most of them". A shape under 0.7px is skipped; under 2.5px it becomes a single mark. Two related substitutions:
    - **LOD dots are batched by colour into one geometry each**, not drawn individually. At the widest zoom nearly every shape lands in the dot path, so one draw call per shape merely moves the bottleneck rather than removing it.
    - **A hatch denser than `MaxHatchLinesPerPixel` is drawn as its filled boundary.** A hatch is the one shape whose cost is unbounded by its size on screen — the generator caps each pattern family at 10,000 segments, so a thumbnail-sized parcel can still submit tens of thousands of strokes that all land on pixels another stroke already covered. This took hatched-parcels zoom p95 from **1038 ms to 3.9 ms**. It is what AutoCAD does.

79. **`Bench/` is the render benchmark, and there is no other way to argue about performance here.** A console app (in the solution, built by CI, **never listed in `installer.iss`**) that builds deterministic scenes, drives scripted camera paths over an offscreen `RenderCanvas`, and reports p50/p95/p99 split into cull/tessellate/raster, plus visible-versus-considered counts, allocation per frame and gen-0 collections, via `Rendering/FrameMetrics.cs`. Baselines live in `Bench/baselines/*.json`. `--png` renders a single frame to an image, because level of detail and the hatch substitution are *visible* changes and a number saying the frame got faster tells you nothing about whether it still shows the right drawing. Scenes are built from a fixed-seed LCG, never `Random`, so a baseline taken on one machine is comparable on another. **Sequencing lesson worth keeping:** the index was integrated before a baseline of the original renderer was captured, so the true pre-change culling numbers were lost. Measure first.

80. **The measured WPF ceiling is ~880 ns per primitive.** After everything above, the remaining wall is WPF itself. On `mixed-cad` at its widest frames — ~100k genuinely visible shapes at ~16px each, which is the stated target workload — a frame costs **88 ms (11 fps)**. That is ~880 ns per shape, squarely in the 600–1500 ns expected of `DrawingVisual` + MilCore. The cause is structural: **WPF has no cosmetic pen**, so zoom-invariant hairlines require setting `Thickness = 1/scale` every frame, and a thickness change invalidates the CPU stroke tessellation of every cached geometry. Caching frozen `StreamGeometry` and pushing a `MatrixTransform` — the obvious fix — lands right back here. Getting past it needs a different raster backend, not more architecture.

81. **`C2VGeometry/Rendering/` holds the one shape-to-primitive type-switch.** `ShapeTessellator` emits into an `IPrimitiveSink`; `TryEmitNative` is what lets one tessellator serve both a rasterizer (which wants everything as segments) and an exporter (which wants a circle to stay a `CIRCLE`). It replaces a `switch (shape)` that had grown to six copies — renderer dispatch, group-child recursion, drawing-tool preview, zoom-extents, and the SVG/PDF/DXF exporters — where adding a shape type meant six edits and the exporters had silently fallen behind. **`Tessellate` returns false for shapes it does not handle, and that return value is not optional**: dimensions, arrows, grids and infinite construction lines have drawing rules the geometry library does not own, and ignoring the result makes them vanish. It did, first time, and cost every dimension on screen. The instance holds scratch buffers and is **not thread-safe** — give each thread its own.

82. **`Rendering/Raster/` is a bespoke software rasterizer, and it exists because the requirement makes one viable.** AutoCAD-crisp means one device pixel, no anti-aliasing, opaque over opaque — which is the single case where a general rasterizer's machinery (coverage accumulation, blitter dispatch, blend-mode resolution, colour management) is all overhead. Anti-aliasing is where rasterizers get genuinely hard, and this requirement removes it. Cohen–Sutherland clip then a DDA walk for hairlines; scanline fill with even-odd/non-zero and holes; screen-space dash expansion; a premultiplied-BGRA colour table that delegates parsing to `ColorConverter` so the two backends cannot disagree about what "Cyan" means. **Costs nothing in packaging**: no NuGet package, no native binary, no `installer.iss` line, and **no `unsafe`** — `Marshal.Copy(int[], 0, IntPtr, int)` onto `WriteableBitmap.BackBuffer` is a safe overload, so the twice-documented `AllowUnsafeBlocks=false` policy stands. It is also pure — an `int[]` in, an `int[]` out — so `Tests/RasterizerTests.cs` runs identically on a GPU-less CI runner, which a golden-image test of a hardware renderer could never promise.
    - **`WriteableBitmap`, not `HwndHost` or a GL control.** A bitmap is ordinary WPF content, so the semi-transparent animation-controls overlay above the canvas still composites and `RenderTargetBitmap` capture for PNG/GIF/MP4 export still works. An HWND-based surface renders above all WPF content and would hide that overlay.
    - **Tessellate once, replay per tile — not the other way round.** The first design had each band walk the scene and let clipping reject what missed its rows: no binning, no synchronisation. But clipping happens *after* tessellation, so a circle was sampled once per band, seventeen times over at 1080p, and **the backend came out slower than the WPF path it was meant to replace**. `RasterCommandBuffer` records the frame once; bands replay it. Don't reverse this.
    - **The raster layer sits beneath the vector layer, so the vector layer must not paint a background when it is active.** It did, and the opaque rectangle hid every rasterised pixel — the geometry simply disappeared and only the grid and WPF-drawn text remained.

83. **The backend is chosen per frame, not configured once** (`RenderCanvas.ShouldUseRasterBackend`, `AppSettingsData.RenderBackend` = `Auto`/`Legacy`/`Managed`). Neither wins outright: the rasterizer pays a fixed ~2 ms a frame at 1080p to clear and copy an 8 MB buffer regardless of content, and in exchange draws primitives far more cheaply than WPF. Measured on `mixed-cad`: the worst frame goes 107 ms → 45 ms, while a near-empty `city-grid` view goes 0.20 ms → 2.19 ms. `Auto` gets both — and on idle it beats *either* fixed choice (6.8 ms Legacy, 5.2 ms Managed, **3.3 ms Auto**) because it switches within the run. **The two thresholds are deliberately different quantities and far apart**: switch up on the previous *vector* frame's measured time (shape count cannot tell a hundred lines from a hundred hatches), switch down on visible-shape count (a raster frame's cost is mostly fixed and says nothing about what vector would have cost). One number in both directions would flap, and because the backends differ in layer ordering, flapping is *visible* — annotation would jump above and below geometry frame to frame. Only a vector frame's time is fed back; timing a raster frame would measure the wrong renderer and latch the choice permanently.

84. **Overlays live in their own visual, so a mouse-move does not rebuild the scene** (`RenderCanvas.RedrawOverlay`). Three layers, bottom-up: raster bitmap, vector scene, overlay. Selection handles, the rubber band, snap markers, the tool preview and the outliner highlight all change on every mouse move while the geometry beneath them is identical — rebuilding the whole scene to move a snap marker four pixels was pure waste, and it is what made drawing and selecting feel heavy on a large drawing. Tool mouse-moves and the `HighlightedShapeId` setter call `RedrawOverlay`; **panning still needs the full redraw**, because the viewport transform changed.

85. **`Shape`'s eight animation fields are behind a lazily-allocated `AnimationState`.** Almost nothing in a drawing is animated, but every shape carried five doubles and two references — about 56 bytes — whether or not it ever moved, which on a million-shape document is 56 MB holding nothing but defaults. The properties keep their names, types and defaults, so no caller changed. Reads never allocate; the first write does. Measured after: 400k shapes in a 318 MB working set, index build 173 ms. A clean before-number was not captured, so no improvement figure is claimed.

86. **The logo is vector, in `Assets/Logo.xaml`, and the app never loads a bitmap for it.** It was a 2048px PNG with a dark textured background baked in, drawn at 120px — so it resampled to a blur, and its opaque square sat on the `#252526` welcome panel as a visibly lighter rectangle, which is what made the screen look like a sticker had been stuck to it. As a `DrawingImage` it is sharp at any DPI, genuinely transparent, and costs a few hundred bytes rather than megabytes in the assembly.
    - **The wordmark is a `TextBlock`, not part of the mark.** Rasterised type at 120px is a grey smear; real type renders with hinting and picks up the theme's font.
    - **Two variants, and the `.ico` ships different artwork per size.** Below about 40px the control polygon and its handle circles are sub-pixel lines that vanish — and on a light taskbar the grey arc goes with them — leaving a red squiggle beside some noise. `LogoMarkSmall` drops the construction detail and thickens what remains. The icon uses the full mark at 256/128/64/48 and the reduced one at 32/24/16.
    - **An `.ico` whose directory entry disagrees with its payload is not a build error.** The previous one declared 256×256 while the embedded PNG was 2048×2048, and carried no small frames at all; the build succeeded and it would simply have looked wrong on other machines. If you regenerate it, check the headers against the payloads.
    - Rendered to PNG/ICO with a throwaway WPF app built **outside** the repository (note 69) — a second `Main()` under the project root breaks the app's build with a duplicate entry point. `img/logo.png` is the README lockup only and is deliberately **not** a `<Resource>`.

87. **`C2VGeometry/Rendering/` is the one shape-to-primitive type-switch, and exporters fall through to it.** Each exporter keeps its own switch mapping a type to that format's native construct — flattening a circle to sixty-four chords in a DXF would make the file useless in a CAD package — but every one of them now ends in a `default` that tessellates instead of falling off the end. That fall-through was the defect: an unrecognised type produced nothing, no error, no trace, and because the switches were written separately they had drifted to cover different subsets. `Tests/ExporterCoverageTests.cs` walks the real public shape surface by reflection and immediately found that **VDimension was dropped entirely from DXF** and **VRadialDimension produced an SVG with no drawing element**. A reflection guard fails when a new shape type is added without being covered.
    - **`ShapeTessellator` now decomposes the annotation shapes it used to decline** — `VArrow`, `VDimension`, `VRadialDimension`, `VRay`, `VXLine` — from their own world-space properties. Its return value is **not optional**: a caller that ignores it drops every shape the tessellator declines.
    - **The dimension label must be a fresh `VText` per call, not a reused one.** Reusing one and mutating it is the obvious optimisation and is wrong: a sink is not obliged to consume text synchronously, and the raster sink defers it to the vector layer holding the reference to end of frame — so every label pointed at the same object and the whole drawing showed a single number. Built inside `Shape.SuspendAutoRegistration()` so it does not land on the canvas.

88. **`D3D11RasterBackend` is the GPU path, and its premise is that navigation costs nothing.** Geometry is uploaded to a vertex buffer **once**, in world coordinates, and a pan or zoom rewrites a single 64-byte constant buffer while the GPU re-transforms and re-clips everything. That is why it is the only backend whose frame time is flat across pan, zoom and idle, and the only one that survives 4K — the two CPU paths copy a full-frame bitmap every frame, 8 MB at 1080p and 33 MB at 2160p, which is over a 60 Hz budget before anything is drawn. `_sceneVersion` on `RenderCanvas` is what tells it the upload is stale; bump it anywhere the shape set changes.
    - **No `unsafe`, verified by spike before a line of it was written** (the plan required this). Device creation, render targets, `CreateBuffer` from a `ReadOnlySpan<T>`, the DXGI shared handle, the D3D9Ex device opened onto it, and `D3DImage.SetBackBuffer` all work through safe managed APIs. `AllowUnsafeBlocks=false` stands.
    - **It fails soft, always.** Hardware device, then WARP, then `IsAvailable` goes false with a reason recorded for the journal and the caller uses a CPU path. A device lost at runtime — driver update, sleep/resume, GPU hang — marks it unavailable for the session rather than throwing once a frame. CI runners have no GPU, so `Tests/D3D11BackendTests.cs` asserts the hardware-independent properties always and the rendering ones only when a device actually exists.
    - **Vortice ships managed-only assemblies** (no `runtimes\win-x64\native`), so they land flat in the build output and each needs its own `installer.iss` line — eight of them.
    - **Measured at 3840×2160, 100k shapes:** city-grid 2.89–3.91 ms across all three camera paths, meeting the ≤4 ms gate; mixed-cad's worst frame 120.9 ms → 44.9 ms. **The residual is text, not geometry** — that frame has ~2,700 labels going through WPF `FormattedText`. Getting past it needs a glyph atlas on the GPU, which is its own piece of work.

89. **`DrawText` clamps its font size, and must keep doing so.** `FormattedText` throws `ArgumentOutOfRangeException` above roughly 35,791 em, and `text.Height * scale` reaches that by simply zooming far enough in. The exception escapes the render pass and takes the process. A glyph that large fills the viewport many times over, so the clamp costs nothing visible. Found because the GPU path initially deferred *every* text in the document rather than the visible ones — which was a second bug, and the reason an off-screen label was being sized at all.

90. **`Animation/Frame.cs` is the requestAnimationFrame model, and it does not replace the timeline.** `Frame.Request(callback)` queues a callback for the next frame; the callback re-requests to keep going and stops asking to end. It exists because composing an `Animator` and adding `Animation` objects to it is a lot of ceremony for "move this a bit each frame". **The timeline stays** because `Animation.Apply(double t)` is a pure function of normalised time, which is what makes it *seekable* — `timeline.Update(t)` is called from six places, including the `TimelinePanel` scrub bar and both the GIF and MP4 exporters, which render the drawing at time T without playing up to it. A self-rescheduling callback is stateful and forward-only and can never offer that.
    - **Two queues, swapped each pump.** A callback that calls `Request` during the pump must run on the *next* frame. Draining one list in place re-enters the callback forever and hangs the UI thread — which is the entire self-rescheduling idiom, so this is not an edge case.
    - **`Frame.Clear()` must run before every execution, and `ModuleCompiler` does it.** User code is compiled into a collectible `AssemblyLoadContext`; a delegate left queued points into that assembly and pins it, so the context never unloads and the previous run's callbacks keep firing against shapes the new run has replaced.
    - **A throwing callback stops the loop.** User code runs in-process; an exception reaching WPF's dispatcher sixty times a second takes the application down. The host reports it to the console instead.
    - The pump re-indexes before repainting, for the same reason the timeline branch does: callbacks mutate shapes in place, so the cull index holds stale boxes. Its clock is separate from `_animationStopwatch`, which starts and stops with timeline playback — a self-rescheduling callback has no notion of being paused.

91. **`DocGenerator.MemberFlags` is what F1 Help lists, and it must include `Static`.** The member tables were reflected with `Public | Instance | DeclaredOnly`, and the consequences were far larger than the omission looks. Every one of the **23 static classes** rendered a page with no members at all — `VColor`, `BooleanOps`, `Chart`, `GlobalParameters`, `ArrayOps`, `GeometryHelper`, `GeometryTolerance`, `CurveGeometry`, `CurveIntersection`, `DoubleExtensions`, `BuiltInHatches`, `HatchGenerator`, `RegionBooleanOps`, `ShapeDefaults`, `Frame`, `EasingFunctions`, `VizConsole`, `SvgExporter` and the extension-method classes — and so did every **static factory on an instance type**: `VCircle.FromCenterDiameter`, the ten `VArc.From*`, `VXYZ.BasisX`/`Zero`, `VTransform.CreateRotationDegrees`, `VRay.AtAngle`, `VXLine.Horizontal`, `Shape.DefaultRegistry`/`AutoRegister`/`Default*`. **339 member descriptions had already been written for members no reader could reach**, which is why the gap survived so long: the prose existed, so a spot-check of the dictionaries looked healthy, and only the rendered page was empty.
    - **An enum declares neither properties nor methods, so property+method tables list nothing.** All 12 public enums rendered empty, including `ColorName` (83 values) and `BuiltInHatch` (73) — the two pages a user is most likely to open precisely *because* they want a name to type. Enums now get a dedicated `Values` section and return early; `GetFields` also covers const fields, which is the entire public surface of `GeometryTolerance`'s tolerance trio.
    - **The flag set is a shared `public const` because there are two consumers.** `HelpWindow` builds its search index with the same reflection call, so the previous duplication meant a member could be listed on a page but unfindable by search (or the reverse). Same class of drift as notes 14/43 — don't re-inline the flags at either call site.
    - **Staticness is printed in the signature column.** It changes how the member is called, and a page mixing `VCircle.FromCenterDiameter` with `circle.Radius` is actively misleading without it. `IsStaticMember` deliberately excludes enum values, which are static fields but would be noise to mark.
    - **`GetDocumentableTypes` must list enums and structs, and rendering a page correctly is worth nothing if the type is not in the tree.** The filter was `IsClass || IsAbstract` — which covers classes *and* interfaces, since an interface is abstract in metadata — so it silently excluded **every enum and every value type**: 15 enums and 5 structs, including `ColorName`, `BuiltInHatch`, `LineType`, `VTextAnchor`, `ParamValue`, `RayHit`, `RayQuery`. The enum-value rendering above was therefore *unreachable* when it was written, and the tests that cover it passed throughout because they call `GenerateDocForType` **directly**. **Reachability and rendering are separate failures and need separate assertions** — `EnumsAndStructsAreReachableInTheTree` is the one that closes this, and any new "the page shows X" test should be paired with a "the type is in the tree" one.
    - **The inherited-description fallback walks the member's real declaring type, not a hard-coded `Shape` then `ICurve`.** The old chain tried those two for *every* type regardless of whether it was one, so any unrelated type with a member called `Name`, `Color`, `Move` or `Intersect` could silently display a description belonging to something else. `GetInheritedMemberDescription` also removes the need to duplicate an entry per subclass — `VCell`'s `VPolygon` members and `StartTime` on all nine animation subclasses resolve through it.
    - **Page titles and `GenerateSyntax` must respect the type kind.** Everything was labelled "X Class", and an enum's syntax line rendered as `public class ColorName : Enum, IComparable, ISpanFormattable…`.
    - Guarded by `Tests/DocGeneratorTests.cs` — 30 cases: static classes, static factories on instance types, enum values, constants, tree reachability, plus the pre-existing duplicate-key and every-page-renders guards. The duplicate-key one still matters most: the three dictionaries are collection initialisers keyed by name, and a duplicate throws out of the constructor and kills Help on open.
    - **The standing verification is a two-way diff, and it is cheap enough to repeat.** After the 2026.8.17 pass: 127 summaries, 86 samples, 1478 member descriptions; **0 keys naming API that does not exist, 0 declared public members in `C2VGeometry`/`Animation`/`Console`/`Export` without a description, 0 duplicate keys.** `Tests/DocumentationAccuracyTests.cs` enforces the first of those on every build; the other two are the reflection diff described under Documentation Ownership.
    - **Known gap:** `SvgExporter` lives in `DoodleSharp.Canvas`, which is *not* in `DocGenerator`'s namespace prefix list, so its page is unreachable in the F1 tree even though it is now documented — as are `SnapType`, `SnapResult`, `SnapEngine`, `DrawingTool` and `DrawingInputMode`, all of which already carry hand-written summaries somebody intended to be seen. Adding the prefix would also surface a dozen genuine app internals (`RenderCanvas`, `QuadTree`, `CodeSyncManager`, …), so this needs a per-type allowlist rather than a prefix.

92. **`VArrow.ArrowheadWings` is the only place arrowhead geometry is computed, and every renderer and exporter must call it.** There were **five** implementations of "where do the wings go" and they disagreed with each other: `RenderCanvas.DrawArrow` and `VArrow.GetArrowheadPoints` hard-coded a `HeadLength / 6` *perpendicular half-width* — an effective ≈9.46° half-angle — and **never read `HeadAngle` at all**; `ShapeTessellator` honoured it but emitted an open V; `PdfExporter` honoured it *and* clamped the head to 20% of the shaft length; `DxfExporter` hard-coded both 30° and `min(length × 0.2, 10)`, ignoring `HeadLength` too. So `HeadAngle` did nothing on screen, silently changed the raster/GPU/PDF/DXF output, and one arrow's head was a different shape *and* size depending on which backend drew the frame or which format it was exported to. This is note 68's failure repeated: **geometry computed per-renderer lets a property be honoured in one path and dropped in another, and nothing fails** — the head still looks like a head.
    - **The contract:** each wing is `HeadLength` long measured *from the tip*, sitting `HeadAngle` degrees off the shaft, so the head spans `2 × HeadAngle`. Closed triangle in every path. Degenerate input returns `(tip, tip)` rather than NaN. Fixing this **widened every arrowhead on screen**, because the canvas was pinned near 9.5° regardless of the property — that is the correction, not a regression, and it is why the change is worth remembering.
    - **Dimension arrowheads were a separate instance of the identical bug** — tessellator at a hard-coded 20°, canvas/SVG/PDF each at a fixed `ArrowSize / 6`. `VDimension.DimensionArrowAngleDegrees` (public const, 20) is now shared by all four. Dimension heads are deliberately *not* per-shape configurable; don't add a property without wiring every path.
    - **`Tests/ArrowheadConsistencyTests.cs` scans the source** of all five files for `ArrowheadWings`/`GetArrowheadPoints` and fails on a reintroduced `/ 6.0;`. A behavioural test alone cannot catch a sixth copy appearing in a path the tests don't render, which is exactly how five accumulated.
    - **Still outstanding: the head is *filled* on the vector backend and *stroked* on the raster and GPU ones.** `DrawArrow`/`DrawDimensionArrowhead` fill the triangle with `GetCachedBrush(shape.Color)` — the **stroke** colour — while the tessellator emits `EmitPolyline(closed: true)`, so the raster and GPU sinks outline it. Closing it needs a way to express "fill this loop in the stroke colour": `IPrimitiveSink.EmitFilledLoops` fills with `PenSpec.FillColor`, which is `Transparent` on a default arrow, so the current API cannot say it. Left as an open item rather than bundled in, because it is a sink API change plus implementations in the raster and D3D sinks. Confirmed by offscreen render (note 69) — geometry matches exactly, only the fill differs.
    - Found while auditing documentation, not by a bug report — the divergence is invisible unless you read the paths side by side. Three neighbouring defects came out of the same reading: `DoubleEnded` was ignored by the PDF, SVG **and** DXF exporters (the start head silently dropped), and `VDimension.ExtensionLength` is inert (see below).
    - **`VDimension.ExtensionLength` controls nothing and is `[Obsolete]`, not deleted.** An extension line spans `OffsetFromOrigin` → `Offset + ExtendBeyondDimLines`, which determines its length completely; nothing ever read `ExtensionLength`. Deprecating rather than deleting keeps existing user code compiling, and the warning is the message (note 70's precedent). It is no longer scaled in `Scale()` — scaling a value that controls nothing only sustained the illusion that it did — but `Clone()` still copies it under a local pragma so a clone reads back what was set.

93. **The overlay layer must be suppressed for any capture of the canvas** (`RenderCanvas.SuppressOverlayForCapture()`). The overlay is a *visual child* of `RenderCanvas` (note 84's three-layer split), and every image and video export renders the canvas itself — so the F10 frame-timing readout, selection handles, the rubber band, snap markers and the measuring overlay were all being baked into exported PNGs, GIFs and MP4s. The scope is an `IDisposable` held for the whole of `ExportCanvasToPng`/`Gif`/`Video`, because each of those captures more than once (the letterbox paths render the canvas into an intermediate bitmap first). **`RedrawOverlay` checks the suppression flag itself** rather than relying on nothing else calling it during a capture — a mouse-move or a `HighlightedShapeId` change would otherwise paint the chrome straight back mid-export. Guarded by a source scan in `Tests/ExportFidelityTests.cs`, since these paths need a real window and cannot be driven from a unit test.

94. **`RenderBackend` has four values, not three, and now has a UI.** `ShouldUseRasterBackend` has always honoured `"GPU"` (force the Direct3D path) alongside `Auto`/`Legacy`/`Managed`, but the property's own XML doc listed only three and **no XAML referenced the key at all** — it was reachable only by hand-editing `%APPDATA%\DoodleSharp\appsettings.json`, which is not a setting a user can be expected to find. It is now a dropdown under `Settings > Application Settings > Rendering`. Matching is case-insensitive and an unrecognised value behaves as `Auto`; the combo mirrors that so a junk value in the settings file shows as Auto rather than blank. Changing it calls `Refresh()` (a full rebuild), not just a repaint, because the backends differ in layer ordering (note 83). Adding a setting to `AppSettingsData` without a UI row is the gap to watch for — the settings grid's `RowDefinitions` count must be grown when rows are added, or the new row silently collapses.

95. **`Animation/Mouse.cs` is the user-code mouse seam, and its registration is *assignment*, not accumulation.** `Mouse.OnMove(h)`/`OnDown`/`OnUp`/`OnClick`/`OnDoubleClick`/`OnDrag`/`OnWheel`/`OnEnter`/`OnLeave` each fill **one slot**; calling one twice leaves the second handler only, and `null` detaches. It looks like it should copy `Frame` (note 90's sibling, same folder, same `CallbackFailed` shape) and it deliberately does **not** copy `Frame.Request`'s handle-based queue. The reason is `ModuleCompiler.ReExecuteResidentAsync`: a Global-Parameters slider drag re-invokes the *same* `Main()` dozens of times a second (note 37), so an additive API would have accumulated hundreds of live handlers in a two-second drag, each running on every mouse move. Assignment makes that structurally impossible — re-running `Main()` N times leaves exactly one handler — and no amount of host-side `Clear()` discipline can achieve the same thing, because the accumulation happens *inside* one run's worth of arming. `Frame` genuinely needs handles (`requestAnimationFrame` queues *n* independent requests); a pointer has one `onmousemove`. **Don't "harmonise" the two APIs.**
    - **Interactive mode is `Mouse.HasHandlers`, and it exists because the canvas already owned every gesture user code would want.** `IsSelectionMode` defaults to **`true`** (`RenderCanvas.cs`) and its `OnMouseDown` branch consumes every left click with `e.Handled = true`, so a click handler would never have fired in the default configuration. While any handler is registered the canvas suppresses **selection, wheel zoom and double-click zoom-extents**; the floating `CanvasNavPanel` (zoom in/out/extents + live zoom %) appears in their place; and the F4 properties panel is hidden and its menu item disabled, because it edits the selected shape and there is no selection. **Middle-drag pan, the drawing tools (P/L/C/R) and the measuring tape are all kept** — pan is the only way to navigate a drawing larger than the viewport, and the two tools are modal states the user armed deliberately. Nothing was deleted: a project registering no handlers behaves exactly as before, which is what makes the whole feature reversible.
    - **Dispatch order in `OnMouseDown` is the crux and is load-bearing:** focus grab (note 20, still first and unconditional) → middle-pan → drawing tool → measuring tool → **user dispatch, which returns** → selection → double-click zoom-extents. Moving the dispatch after the selection branch reinstates the original bug; moving it before the tool branches lets a script break the line tool. `Tests/MouseWiringTests.cs` pins both orderings by source scan, because these handlers need a real window and no unit test can drive them.
    - **There is no `Handled`/`preventDefault` flag, on purpose.** Because interactive mode suppresses the competing gestures *wholesale* rather than arbitrating per event, there is nothing left for a handler to cancel — a `Handled` property would have controlled nothing, which is exactly the defect note 92 records for `VDimension.ExtensionLength`. Don't add one without first giving it something to do.
    - **`MouseInfo` references no WPF type** (coordinates are `VXYZ` and plain `double`; buttons and modifiers are its own enums). That is what lets the entire registry be driven from a plain xunit worker with no window, no STA thread and no synthetic input — `Tests/MouseCallbackTests.cs` is 45 cases against it. `RenderCanvas.BuildMouseInfo` is the single place `Keyboard.Modifiers`/`MouseButton` are read. **`MouseInfo.Target` is lazy and memoised** (a `Func<VXYZ, Shape?>` closure over `SelectionTool.HitTest`) because a move handler runs 100+ times a second and most never ask what is under the cursor; it hit-tests **`RawPosition`**, since testing the grid-snapped point would report whatever sits at the snap intersection. A fresh payload is allocated per event and **never pooled** — a recycled instance would appear to mutate under any handler that stored it.
    - **`Clear()` belongs at every ALC boundary**, for the same pinning reason as `Frame.Clear()` (note 90): `ModuleCompiler.CompileAndExecuteAsync`, `ReExecuteResidentAsync`, `InvalidateResident` (inside the `ctx != null` branch **only** — it is also called on a programmatic source edit and a project switch, where clearing would kill a running animation for nothing), `SketchRuntime.Stop`, and `MainWindow.StopAllAnimations`. `MouseWiringTests` asserts the `Frame.Clear()` and `Mouse.Clear()` counts are **equal** per file, which is what stops one drifting out of sync with the other.
    - Chrome is synced by `MainWindow.SyncInteractiveModeChrome`, driven off `Mouse.HandlersChanged` (marshalled — `Main()` runs on a thread-pool thread) plus a call at the end of every run path, **not** per slot assignment, or a `Main()` assigning several handlers would flicker the panel.

96. **Repainting after per-frame user code needs `SetFrameShapes`, not `Refresh()` — a shape *created* by a callback is otherwise invisible.** `CanvasRenderer.AddShape` appends only to the registry's own `_shapes` list; `RenderCanvas._currentShapes` is a separate `ToList()` snapshot assigned only by `Render()` and `SetFrameShapes()`. So `Refresh()` repaints the snapshot as it stood when the run finished. A callback that *mutates* an existing shape works fine, which is exactly what made this asymmetry survive so long — it was already live in the `Frame` path (note 90), where `ReindexForAnimationFrame() + Refresh()` meant a `Frame` callback creating a shape drew nothing. `MainWindow.RepaintAfterUserCode` is now the single repaint used by both the `Frame` pump and the `Mouse` dirty-flag hook: it compares `CanvasRenderer.RegistryVersion` (bumped on add/remove/reorder/clear, **not** on mutation) and takes the cheap re-index when only positions moved, the full re-snapshot when the set changed. **Mouse dispatch is synchronous but the repaint is deferred to one per frame** via `Mouse.ConsumeSceneDirty()`, so a burst of moves coalesces into a single redraw and note 84 is not regressed. Any handler that ran marks the frame dirty — we cannot tell whether it touched the scene, and one redundant repaint is invisible whereas a missed change reads as a broken API.

97. **`Sketch.MouseX`/`MouseY`/`MousePressed` were dead for their whole existence, and the writer had zero callers.** All five polled input properties (`Sketch.cs`) were declared, documented in README and F1 Help, and permanently at their defaults, because `SketchRuntime.UpdateInputState` — their only writer — was never called from anywhere in the repo. `RenderCanvas` now records the pointer into `Mouse` **unconditionally**, outside the `HasHandlers` gate (`TrackPointer`, three field writes — cheap enough for the hot path), and `SketchRuntime.PopulateState` reads it back through that same `UpdateInputState`. So `Mouse.X`/`Y`/`IsDown` are usable with no handler registered, which is what makes them work from a `Frame` callback or a sketch's `Draw()`. **`KeyPressed`/`LastKey` still have no source** and remain inert — `RenderCanvas.OnPreviewKeyDown` early-returns unless a drawing tool is mid-input, so the write site would have to be `MainWindow_PreviewKeyDown` gated on `IsKeyboardFocusWithin`. Fix those two or soften their docs; don't leave them claiming to work.

98. **`AppSettingsData.ShowToolbar` is gone: it governed a drawing toolbar that no longer exists.** `MainWindow.xaml` replaced the toolbar with the Draw menu, the menu item went with it, and `ShowToolbarMenuItem_Click` had been reduced to an empty stub — nothing read or wrote the setting. Removal is safe because `ApplicationSettings.Load` uses default `JsonSerializerOptions`, which ignore unknown members, so an older `appsettings.json` still carrying the key deserializes fine and drops it on the next save. The related audit is worth repeating when a UI element is retired: grep the setting name across `*.cs` **and** `*.xaml` — a setting with zero of both is dead, and one with a reader but no XAML is note 94's opposite failure (reachable only by hand-editing JSON).

99. **F1 Help renders an `Events` section, because before it no public event appeared anywhere.** `GenerateDocForType` listed Constructors / Values / Properties / Fields / Methods, and the methods query drops an event's `add_`/`remove_` accessors as `IsSpecialName` — so nothing called `GetEvents` and **all five public events across the documented namespaces were unreachable**: `Mouse.CallbackFailed`, `Frame.CallbackFailed`, `GlobalParameters.Changed`, `GlobalParameters.Reloaded`, `ConsoleOutput.OutputChanged`. **Four of the five already had descriptions written**, which is note 91's exact shape and why it survived: the prose exists, so auditing the dictionaries looks healthy and only the rendered page is missing them. Three parts had to move together, and they are the parts to keep in step: `GenerateMemberTable` needed an **`EventInfo` arm** (an event has no `PropertyType`/`ReturnType`, so its row rendered with a blank signature cell), `IsStaticMember` needed one too (staticness lives on the accessors, so a static event read as an instance member), and `HelpWindow`'s search index needed its own `GetEvents` loop — it builds from the same `DocGenerator.MemberFlags` precisely so a member cannot be listed on a page but be unfindable by search. Guarded by `PublicEventsAppearOnTheirPage` and `StaticEventsAreFlaggedStatic` in `Tests/DocGeneratorTests.cs`. **When adding a member *kind* to the docs, there are always three sites: the section, the signature switch, and the search index.**

100. **`MainWindow`'s content area is an AvalonDock `DockingManager`, and panel identity is `ContentId`, not `x:Name`.** The old nine-column `Grid` (editor | canvas+console | project browser | properties | global parameters, each toggled by writing `Width="0"` and a matching splitter `Visibility`) is gone, along with roughly 570 lines of hand-rolled layout code: nine near-identical `Set*Visibility` methods, five `GridSplitter`s, the manual `ConsoleSplitter` mouse-drag, and `PropertiesWindow`. Panels are `LayoutDocument` (Code, Settings) or `LayoutAnchorable` (everything else); the **Ribbon and Minimap stay out of it** — a command strip and an editor gutter are not tool windows.
    - **`ContentId` is the stable identity a saved layout refers to, and is deliberately decoupled from `x:Name`.** Renaming one invalidates every user's saved arrangement, so they are namespaced `ds.document.*` / `ds.tool.*` and pinned by `Tests/DockingLayoutTests.cs`, which also asserts every id in the XAML is registered in the code-behind — the failure that otherwise produces a menu entry that silently does nothing.
    - **Show/hide has exactly one implementation, and `IsVisibleChanged` is its only writer.** A menu click only ever calls `Show()`/`Hide()` on the pane; the pane's own visibility change writes the checkmark, the settings key and any side effect (canvas → `RunButton`/`DrawMenu` enablement; global parameters → `Rebuild()`). That is what makes the menu track a panel closed by its own X button or dragged out of a pane. The previous design maintained those in parallel and had drifted — `SetConsoleVisibility` re-derived its own menu check from `ConsoleTab.Visibility`, and the console's panel-plus-tab visibility carried a documented start-up ordering hazard. **`Hide()`, never `Close()`:** Close removes an anchorable from the tree permanently, which turns its menu entry into a one-way trip.
    - **Sizing: let the document pane fill, and give tool columns concrete widths.** A `DockWidth="2*"` on the `LayoutDocumentPaneGroup` starved its siblings to zero width — the canvas and console existed and reported `IsVisible == true` while being invisible. AvalonDock gives the document area the remaining space and sizes tool panes from `DockWidth`; don't put star widths on the document group.
    - **AvalonDock 5 has no `XmlLayoutSerializer`.** It exposes `AvalonDock.Serialization.LayoutDtoMapper` (an *instance*, not a static) mapping the layout to an `[XmlRoot]`-attributed `LayoutRootDto`, which the host serializes itself — `Docking/LayoutFile.cs` wraps that in a `schema`-stamped envelope. `Descendents` is an extension method on `AvalonDock.Layout.Extensions`, and floating-window geometry lives on the positionable group (`LayoutAnchorableFloatingWindow.RootPanel`), not on `LayoutFloatingWindow`. All four of these differ from the v3/v4 API every tutorial shows — check the assembly, not the samples.
    - **A restored layout carries arrangement and ids only, never controls**, so every pane comes back empty and `ReattachPanelContent` re-binds them by ContentId — and `RebindPanesAfterRestore` re-points the registry at the *new* pane objects, or every menu toggle would act on a pane belonging to the discarded layout. **A registered panel the file does not mention is re-inserted hidden** (`LayoutFile.FindMissingIds`): AvalonDock simply omits a panel added since the layout was saved, so without this it would not exist at all.
    - **A layout is a preference, so there is no migration path.** A file whose `schema` does not match `LayoutFile.CurrentSchema` is discarded whole and the default used; bump the schema when a ContentId is renamed or removed. Falling back costs nothing because the default is already loaded — `_defaultLayoutXml` is captured from the live tree in the constructor **before anything mutates it**, which is why that ordering is load-bearing and why the default cannot drift from the markup. Reset Layout (View menu *and* the `Ctrl+R` key handler — two call sites) restores it, plus the Ribbon and Minimap, which the layout file does not describe.
    - **Off-screen recovery** (`Docking/ScreenBounds.cs`) runs after every restore: a floating panel whose caption is not grabbable on the current virtual desktop is *clamped* back, not centred, so a panel parked on the right stays on the right. It takes the desktop rect as a parameter so the arithmetic is unit-testable — including a monitor placed left of primary, which makes the virtual desktop origin negative and breaks any clamp written against `[0, width]`. Uses `SystemParameters`, not WinForms (note 40).
    - Verified in the running app: the canvas renders through the **GPU backend while floated in a separate window** (`IsAvailable=True, Output=D3DImage`), a hidden pane keeps its content laid out, AvalonEdit floats cleanly, and `MainWindow`'s `PreviewKeyDown` **still sees keys from a floating pane** because AvalonDock keeps floated content logically parented to the `DockingManager` — so the F5/Ctrl+R/F9 shortcuts did not need re-scoping. Re-check that last one if the shortcut handling ever moves off `PreviewKeyDown`.

  the API documentation pass itself.

- Its standard is **every public type and every public member documented, each with a working
  example** — the C2VGeometry API plus `DoodleSharp.Animation` and `DoodleSharp.Console`.
- `CLAUDE.md`, `CHANGELOG.md` and `docs/*` stay with the main session: they are engineering notes and
  release history, not API documentation.

Launch it with the Agent tool, `subagent_type: "docs-author"`. It reads the source before writing
examples, so give it the diff or feature area rather than a list of prose to insert. For a full audit,
launch **two** agents with disjoint file ownership — one on `README.md`, one on
`Documentation/DocGenerator.cs` — so they run in parallel without conflicting on a file.

**Give the agent a reflection dump, not a reading list.** Note 62 is the reason: prose review has
repeatedly failed to notice documented API that does not exist, because a fabricated member reads
exactly like a real one. The check that works is a diff, and it is cheap:

1. `dotnet build DoodleSharp.sln -c Release`, then dump the public surface of the **built**
   `C2VGeometry.dll` and `DoodleSharp.dll` by reflection — every type with its constructors,
   properties, fields, events, methods (parameter names *and* default values), interfaces, enum
   values and `[OBSOLETE]` markers — plus a flat `Type.Member` index with inherited members included.
   Build the dumper **outside the repository** (note 69: a second `Main()` under the project root
   breaks the app's build with a duplicate entry point).
2. Extract the keys of `_summaries`, `_csharpSamples` and `_memberDescriptions`, and diff both ways.
   `documented − real` is fabricated API and must be fixed. `real − documented` is the work list.
3. Namespaces to hold to the "every member documented" standard: `C2VGeometry`,
   `DoodleSharp.Animation`, `DoodleSharp.Console`, plus the exporters. `DoodleSharp.Canvas` types
   (`RenderCanvas`, `SelectionTool`, `SnapEngine`, `QuadTree`, `ViewportTransform`, …) are app
   internals and out of scope — but `SvgExporter` lives there and *is* in scope.

## /release Command

When the user says "/release", "cut a release", "ship a release", or "release":

1. **Delegate the API documentation pass to the `docs-author` subagent, then run `/update-docs`**, so the
   release ships with current documentation. The agent covers `README.md` and `DocGenerator.cs`;
   `/update-docs` then handles `CHANGELOG.md`, `CLAUDE.md` and `docs/*`. Commit + push the doc changes as a *separate* commit before bumping the
   version. **Do not skip the agent** — it is the standing owner of the user-facing docs, and a release
   whose API documentation was not reviewed by it is not ready to cut.
2. **No version to choose — versioning is calendar-based (`YEAR.MONTH.PATCH`).** The script stamps `YEAR`/`MONTH` from today's date and increments `PATCH` within the same month (resetting to 0 the first time you release in a new month or year). E.g. the second May 2026 release is `2026.5.1`; the first June release is `2026.6.0`.
3. **Run `scripts\release.ps1`** (no `-Bump`) — it guards working-tree cleanliness, computes the calendar version, writes it into `Directory.Build.props` + `installer.iss` (the two version sources, kept in sync because Inno Setup doesn't read MSBuild props), commits as "Release v<new>", tags `v<new>`, and pushes main + tag to origin. Pass `-LocalBuild` to also build Release configs + installer locally for smoke-testing; CI publishes the canonical artifacts regardless.
4. **Tag push triggers `.github/workflows/release.yml`** on `windows-latest`: it verifies `Directory.Build.props` matches the tag, builds `DoodleSharp.sln` in Release, runs the test suite, invokes Inno Setup (`ISCC.exe`, pre-installed on the runner) to produce `installer/output/DoodleSharp-<new>-Setup.exe`, then publishes the GitHub release with the installer attached. **Release notes are generated from `git log <prev-tag>..<tag>`** (commit subjects, excluding the `Release v*` bump commits) — *not* `--generate-notes`, which produces only a bare compare link here because the repo commits directly to `main` with no PRs. The curated human summary lives in `CHANGELOG.md` (updated during `/update-docs`). Watch progress at `https://github.com/harilalmn/DoodleSharp/actions/workflows/release.yml`.

Never bump versions by hand — the script is the only thing that touches both `Directory.Build.props` and `installer.iss`. Never create a `v*` tag by hand either — the workflow's "verify props match tag" step fails fast if `Directory.Build.props` is out of sync with the tag, which is what catches hand-tagged releases.
